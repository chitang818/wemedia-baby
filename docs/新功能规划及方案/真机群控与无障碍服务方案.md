# 真机群控与无障碍服务 —— 技术验证方案

> **文档定位**：本文档是对 [发布系统技术方案讨论](./发布系统技术方案讨论.md) 中"方案四：转换赛道——真机群控与无障碍服务"的深度展开。目标是在正式实施前，先以最小成本跑通核心链路、验证可行性与风控安全性，为后续是否纳入主线产品提供数据依据。

---


## 一、方案回顾与核心假设

### 1.1 为什么要验证这条路线

媒小宝当前的发布能力完全依赖"PC 浏览器 + Playwright"。尽管我们已有 stealth.js、undetected-playwright、指纹伪装、拟人行为等多层防风控手段，但 Web 端始终面临一个根本问题：**浏览器把自身的一切暴露给了平台的 JS 沙箱**。Canvas 指纹、WebGL 渲染器、AudioContext、高精度时序——平台有太多维度来"审视"你的浏览器是不是真的。

而 App 端的世界完全不同：

- **指纹采集维度远少于 Web**：Android 应用受权限模型限制，采集 Canvas/WebGL/字体列表等信号的能力远弱于浏览器。
- **操作系统级自动化无需注入**：无障碍服务（AccessibilityService）是 Android 官方提供的系统级能力，App 进程无法区分来自无障碍服务的操作与真实用户触摸。
- **物理设备 = 天然多指纹**：每台真机的 IMEI/OAID/Android ID/MAC/基带版本/传感器噪声天然不同，无需伪造。
- **网络环境天然分散**：每台手机可以独立走运营商蜂窝网络或独立 Wi-Fi，IP 多样性远高于单机多浏览器方案。

**核心假设**：在真实 Android 设备上，通过无障碍服务驱动 App 完成视频发布，被平台风控识别的概率将显著低于任何浏览器自动化方案。

### 1.2 验证目标

| 编号 | 验证项 | 成功标准 |
|:---:|--------|---------|
| V1 | ADB 连接与设备管理 | 能从 PC 稳定管理 ≥3 台 Android 设备（USB / Wi-Fi ADB） |
| V2 | 文件推送 | 能将视频/图片文件高效推送到手机指定目录，App 能正确识别 |
| V3 | App 启动与页面导航 | 能通过无障碍/UiAutomator 启动抖音/快手 App 并导航到发布页 |
| V4 | 表单填写 | 能自动填写标题、描述、话题标签等文本字段 |
| V5 | 视频选择与上传 | 能从相册选择已推送的视频并触发上传 |
| V6 | 发布与结果校验 | 能点击发布按钮，并通过 UI 状态判断发布成功/失败 |
| V7 | 多设备并发 | ≥2 台设备可同时执行发布任务，互不干扰 |
| V8 | 风控表现 | 在真机上发布的账号无异常提示、无限流、无封号（对照 Web 端） |

## 二、核心决策：独立验证工具 vs 集成到主项目

这是本次方案需要首先回答的关键架构问题。下面从多个维度进行对比分析。

### 2.1 方案对比矩阵

| 维度 | 独立验证工具 | 集成到主项目 |
|------|------------|------------|
| **开发速度** | ⭐⭐⭐⭐⭐ 快。可以完全不受现有 UI 框架、插件体系、流水线的约束，自由选择最简技术栈 | ⭐⭐ 慢。需要先理解并遵循现有架构约定（插件接口、流水线 Filter、ORM 模型、事件总线等），改动面大 |
| **试错成本** | ⭐⭐⭐⭐⭐ 极低。验证失败直接丢弃，不影响主线任何一行代码 | ⭐⭐ 高。即使用 feature flag 隔离，也会在主线留下大量实验性代码和分支逻辑 |
| **数据复用** | ⭐⭐⭐ 中等。可以读主项目的 SQLite 数据库（账号信息、素材库），但需要额外建立 ORM 模型映射或直接 SQL 查询 | ⭐⭐⭐⭐⭐ 高。直接复用 Tortoise ORM 模型、AccountService、素材库服务等 |
| **UI 交互** | ⭐⭐⭐ 需要自建简易 UI（可以是命令行/Web/简易 Qt 面板） | ⭐⭐⭐⭐ 可以复用现有的 PySide6 UI 体系，但需要新增页面和适配 |
| **代码质量** | ⭐⭐⭐ 验证阶段代码通常较"糙"，后续集成时需要重构 | ⭐⭐⭐⭐⭐ 一开始就在正式架构下编写，后续无需二次重构 |
| **对主线稳定性的影响** | ⭐⭐⭐⭐⭐ 零影响 | ⭐⭐ 有风险。新增的 ADB/无障碍依赖、后台进程管理可能引入崩溃或资源泄漏 |
| **验证周期** | 预计 1~2 周可跑通核心链路 | 预计 3~4 周，大量时间花在适配现有框架 |

### 2.2 推荐决策：独立验证工具 + 共享数据库

**建议采用"独立验证工具"路线**，理由如下：

1. **验证阶段的首要目标是"证明可行"，不是"做产品"**。无障碍服务方案涉及 ADB 连接稳定性、Android 无障碍权限配置、不同手机品牌/系统版本的兼容性、大文件推送性能等大量未知风险。在主项目中做这些探索，试错成本过高。

2. **数据可以共享，代码不必耦合**。验证工具可以直接读取主项目的 SQLite 数据库（`%LOCALAPPDATA%\WeMediaBaby\data\database.db`），复用已有的账号数据和素材路径。但执行逻辑完全独立，不污染主线代码。

3. **验证成功后再规划集成路径**。一旦核心链路跑通且风控表现良好，我们可以将验证工具中沉淀的核心能力（ADB 管理器、无障碍脚本引擎、App 操作录制器）提取为独立模块，按照主项目的插件接口（`PublishPluginInterface`）封装后接入发布流水线。

4. **失败代价最小**。如果验证发现方案不可行（比如主流 App 已能检测无障碍服务、或真机运维成本不可接受），独立工具直接废弃，主项目毫发无损。

### 2.3 独立工具与主项目的边界

```
┌─────────────────────────────┐      ┌──────────────────────────────┐
│     媒小宝主项目 (现有)       │      │    真机群控验证工具 (新建)      │
│                             │      │                              │
│  ┌─────────┐ ┌────────────┐ │      │  ┌──────────┐ ┌───────────┐ │
│  │ 账号管理 │ │ 素材/文案库 │ │      │  │ ADB管理器 │ │ 设备监控  │ │
│  └────┬────┘ └─────┬──────┘ │      │  └────┬─────┘ └─────┬─────┘ │
│       │            │        │      │       │             │       │
│  ┌────▼────────────▼──────┐ │      │  ┌────▼─────────────▼─────┐ │
│  │   SQLite 数据库         │◄├──────├─►│  直接读取主项目数据库    │ │
│  │   database.db           │ │ 共享 │  │  (只读 / 写入发布记录)  │ │
│  └────────────────────────┘ │      │  └────────────────────────┘ │
│                             │      │                              │
│  ┌────────────────────────┐ │      │  ┌────────────────────────┐ │
│  │ Playwright 发布插件     │ │      │  │ 无障碍服务发布脚本      │ │
```

**共享规则**：
- 验证工具**只读**主项目数据库中的 `platform_account`（账号信息）和素材相关表
- 验证工具可以**写入**自己的发布记录到 `publish_record` 表，但需标记 `publish_channel = "mobile_a11y"`（无障碍服务通道），与 Web 端记录区分
- 验证工具**不修改**主项目的任何配置文件或代码

### 3.2 技术栈选型

| 层级 | 技术选择 | 选择理由 |
|------|---------|---------|
| **PC 端语言** | Python 3.12（与主项目一致） | 复用主项目的虚拟环境和依赖体系，共享 ORM 模型定义 |
| **ADB 通信** | `adbutils`（纯 Python ADB 客户端） | 无需单独安装 ADB 命令行工具，API 友好，支持异步 |
| **Android 自动化** | **方案 A：UiAutomator2**（`uiautomator2` 库）<br>**方案 B：Appium + UiAutomator2** | 方案 A 更轻量、部署简单，验证阶段优先；方案 B 更成熟但依赖 Node.js 服务端 |
| **设备端无障碍** | ATX（Android Test eXtended） | `uiautomator2` 自带的 ATX Agent，自动部署到手机，提供 HTTP API 控制 |
| **控制台 UI** | 第一阶段 CLI（`click`/`rich`）<br>第二阶段可选 Web（`FastAPI` + 简易前端） | 验证阶段 CLI 足够，无需花时间在 UI 上 |
| **数据库访问** | `aiosqlite` + 直接 SQL 或复用主项目 Tortoise ORM 模型 | 灵活选择：可以最小依赖直接 SQL，也可以 import 主项目模型 |
| **屏幕镜像/调试** | `scrcpy`（可选） | 开发调试阶段用于实时观察手机屏幕，不是必须组件 |

### 3.3 关于 UiAutomator2 vs 纯无障碍服务的选择

在 Android 自动化领域，有两种主流路线：

**路线 A：UiAutomator2（推荐验证阶段使用）**
- 本质是 Google 官方的 UI 测试框架，运行在设备端的 Instrumentation 进程中
- 通过 `uiautomator2` Python 库可以从 PC 端远程控制
- 优点：API 成熟、社区活跃、文档完善、元素定位能力强（支持 XPath/ResourceId/Text）
- 缺点：Instrumentation 进程可能被部分 App 检测（但概率远低于浏览器自动化被检测的概率）

**路线 B：自定义 AccessibilityService**
- 开发一个 Android APK，内含自定义的 AccessibilityService
- 通过 ADB 或 Socket 从 PC 端下发指令，无障碍服务执行操作
- 优点：更隐蔽，无 Instrumentation 痕迹，系统级权限
- 缺点：需要额外开发 Android 应用，元素定位能力不如 UiAutomator2 丰富

**验证阶段建议**：先用 UiAutomator2 快速跑通全链路。如果发现被 App 检测，再切换到自定义 AccessibilityService 方案。这两种方案的 PC 端控制逻辑几乎完全一致，切换成本低。

## 四、核心流程设计

### 4.1 一次完整的"真机发布"流程

```
用户在控制台发起发布任务
    │
    ▼
① 任务调度器从数据库读取任务参数
   （账号、平台、视频路径、标题、标签等）
    │
    ▼
② 设备管理器分配空闲设备
   （检查设备在线状态、当前是否有任务在执行）
    │
    ▼
③ 文件推送阶段
   ├─ adb push 视频文件到手机 /sdcard/DCIM/ 目录
   ├─ 触发 MediaScan 让相册识别新文件
   └─ 校验文件完整性（MD5 对比）
    │
    ▼
④ App 启动与导航
   ├─ 通过 am start 启动目标 App
   ├─ 等待首页加载完成
   └─ 点击"发布"/"+"按钮进入发布流程
    │
    ▼
⑤ 素材选择
   ├─ 在相册选择器中定位刚推送的视频
   ├─ 选中并确认
   └─ 等待视频处理/裁剪页面
    │
    ▼
⑥ 表单填写
   ├─ 输入标题（逐字输入，模拟真人节奏）
   ├─ 输入描述
   ├─ 添加话题标签
   ├─ 设置封面（可选）
   └─ 其他平台特有字段
    │
    ▼
⑦ 发布执行
   ├─ 点击"发布"按钮
   ├─ 等待上传进度完成
   └─ 检测发布成功/失败的 UI 状态
    │
    ▼
⑧ 结果回写
   ├─ 截图保存（成功/失败状态）
   ├─ 写入 publish_record 表
   └─ 清理手机上的临时文件
```

### 4.2 设备生命周期管理

| 状态 | 含义 | 转换条件 |
|------|------|---------|
| `idle` | 空闲可用 | 任务完成或初始上线 |
| `busy` | 正在执行任务 | 被调度器分配任务 |
| `error` | 异常（断连/无响应） | ADB 连接丢失、App 崩溃 |
| `cooldown` | 冷却期 | 任务完成后主动休息（防风控） |
| `offline` | 离线 | USB 断开或 Wi-Fi ADB 不可达 |

### 4.3 防风控策略（App 端特有）

虽然真机方案本身就比浏览器方案安全很多，但仍需注意以下细节：

1. **操作间隔随机化**：每步操作之间插入 0.5~3 秒的随机等待，模拟真人浏览节奏
2. **输入速度拟人化**：文字输入速度控制在 2~5 字/秒，带随机波动
3. **设备冷却期**：单设备连续发布 2~3 个视频后强制休息 10~30 分钟
4. **App 前台时长**：发布前可以先在 App 内浏览 30~60 秒，模拟正常使用
5. **避免Root**：尽量使用非 Root 设备，Root 状态可能被 App 检测
6. **网络多样性**：不同设备使用不同网络出口（蜂窝数据 / 不同 Wi-Fi）

## 五、需要提前评估的风险与挑战

### 5.1 技术风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| **App UI 更新频繁**：抖音/快手等 App 每 1~2 周更新一次，UI 布局可能变化 | 高 | 使用 ResourceId 定位优先（比 XPath 稳定），建立元素定位配置文件，UI 变化时只改配置 |
| **UiAutomator2 被检测**：部分 App 可能检测 Instrumentation 进程 | 中 | 备选方案 B（自定义无障碍服务），或使用 `Shizuku` 等非 Root 授权方案 |
| **大文件推送慢**：通过 USB 2.0 推送 1GB 视频可能需要 2~3 分钟 | 中 | 使用 Wi-Fi ADB（局域网传输更快），或预先批量推送素材 |
| **Android 版本碎片化**：不同厂商、不同 Android 版本的系统 UI 差异 | 中 | 验证阶段先限定统一机型和系统版本，后续再扩展兼容性 |
| **无障碍服务权限被系统回收**：部分厂商ROM会自动关闭无障碍权限 | 中 | 使用 `adb shell settings` 命令持久化无障碍配置，或引导用户关闭电池优化 |

### 5.2 运维风险

| 风险 | 严重程度 | 缓解措施 |
|------|---------|---------|
| **设备发热与续航**：长时间运行自动化任务导致手机过热 | 中 | 设置冷却周期，使用散热机架，保持充电状态 |
| **USB 连接不稳定**：USB Hub 供电不足或接触不良 | 中 | 使用带独立供电的工业级 USB Hub |
| **App 登录态失效**：App 长时间未使用可能要求重新登录 | 低 | 定期心跳检测登录状态，失效时通知用户手动登录 |

### 5.3 成本评估

| 项目 | 单价估算 | 备注 |
|------|---------|------|
| Android 手机（二手/低端机） | 200~500 元/台 | 验证阶段 3~5 台足够，推荐小米/红米（AOSP 兼容性好） |
| USB Hub（7口带供电） | 50~100 元 | 一个即可 |
| 手机支架/机架 | 50~200 元 | 可选，开发阶段随意摆放也行 |
| SIM 卡（流量卡） | 20~50 元/月/张 | 如需独立网络出口 |
| **验证阶段总成本** | **约 1000~3000 元** | 主要是手机采购 |

## 六、分阶段验证路线图

### 第一阶段：环境搭建与基础通信（预计 3~5 天）

**目标**：跑通 PC → Android 设备的完整控制链路

- 搭建独立验证工具项目骨架（Python 项目，独立虚拟环境或复用主项目 venv）
- 实现 ADB 设备发现、连接、状态监控
- 实现文件推送（adb push + MediaScan）
- 实现屏幕截图获取（用于调试）
- 实现 UiAutomator2 连接与基础操作（点击、滑动、文本输入）

**交付物**：能通过 CLI 命令向手机推送文件、启动 App、执行简单点击

### 第二阶段：单平台发布流程打通（预计 5~7 天）

**目标**：在一个平台上完整跑通从素材推送到发布成功的全链路

- 选择**抖音**作为第一个验证平台（用户最多、风控最严、验证价值最高）
