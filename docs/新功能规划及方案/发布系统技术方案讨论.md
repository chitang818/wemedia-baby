# 发布系统终极防风控技术方案推演与探讨

> **背景**：针对媒小宝当前采用的“Playwright + 真实 Chrome + stealth.js”的应用层防风控方案，在面对小红书、抖音等平台日益严苛的风控体系时可能面临的瓶颈，本文档收录了关于如何突破 JS 沙箱限制、实现“降维打击”的高级自动化方案探讨。

目前的方案在行业内被称为 **“应用层伪装方案”**。其优点是易于开发和后台并发，但核心缺陷在于它依然运行在平台的规则内（JS 沙箱内），平台始终有办法通过极端的特征嗅探探测到自动化底层的蛛丝马迹。若要追求更极致的安全，可以考虑以下几个方向的演进或替代：

---

## 方案一：内核级重编译（防检测的 Web 端天花板）

目前项目的 `stealth.js` 是在页面加载时修改 JS 对象（例如重写 Canvas 原型链）。但现代高级风控能通过 `toString()` 校验、原型链溯源等方法，发现函数被篡改。

*   **实现机制**：拉取 Chromium 的 C++ 源码。在源码层直接修改 Canvas 渲染引擎、AudioContext 缓冲逻辑、写死 WebGL 厂商信息等，然后重新编译出属于自己的专属浏览器内核（此即市面上高价“指纹浏览器”的核心技术）。
*   **优势**：**绝对安全**。从底层吐出来的特征原生如此，JS 原型链毫无篡改痕迹，风控探针无从查证。
*   **劣势**：**维护成本极高**。每次 Chrome 版本升级都需要重新合并代码并编译，需要有经验的 C++ 底层开发团队。

## 方案二：无 CDP 模式（Chrome Extension 驱动）

Playwright 哪怕抹除了 `navigator.webdriver`，依然需要开启 `--remote-debugging-port`，并通过 Chrome DevTools Protocol (CDP) 来控制浏览器。高级风控可以检测到调试端口，或通过特定事件的时序发现 CDP 的痕迹。

*   **实现机制**：完全抛弃 Playwright。编写自研的 **Chrome 浏览器插件 (Extension)** 安装到浏览器中。通过本地 WebSocket Server 下发任务，插件通过后台脚本 (Background Worker) 接收任务，再通过内容脚本 (Content Script) 直接操作 DOM 节点。
*   **优势**：**启动零痕迹**。浏览器以 100% 正常用户的方式启动，没有调试参数和自动化标识。
*   **劣势**：**沙箱权限受限**。例如上传本地视频时，插件安全限制使其无法直接赋值给 `<input type="file">`，必须配合 Native Messaging 技术或本地代理中转文件流来突破。

## 方案三：硬件级/驱动级输入与混合架构（推荐研究方向）

我们目前的“拟人点击”本质上仍是 CDP 协议发送的 `mouse.click` 合成事件。

*   **实现机制**：
    1.  **驱动级**：调用操作系统的底层 API（如 Windows 的 `SendInput`，甚至使用易语言/大漠插件挂载 Ring3/Ring0 级驱动），接管整台电脑的光标移动和键盘事件。
    2.  **纯物理级**：通过树莓派等设备伪装成标准 USB 鼠标和键盘，物理层发送信号。
*   **优势**：**绝对真实的系统事件**。平台获取到的是操作系统底层中断，世上没有任何 JS 脚本能区分这是软件控制还是真人挥动鼠标。
*   **劣势**：**丧失多账号并发能力**。一台电脑只有一个鼠标指针，机器在这几秒钟内必须独占焦点。

### 🌟 针对媒小宝的终极变种方案：“DOM辅助定位 + 系统真实点击”

**由于媒小宝当前的发布队列是单线程运行的，并发限制不再是缺点。** 我们可以采用一种极其强大的混合架构，兼顾 Playwright 的稳定性与底层驱动的绝对安全性：

1.  **固定参照系**：将 Chrome 强制在屏幕左上角固定分辨率（或全屏）打开，确保网页视口坐标能与 Windows 绝对物理坐标对齐。
2.  **Playwright 做眼睛**：代码中不再调用任何 `locator.click()`，仅使用 Playwright 瞬间获取元素在屏幕上的物理坐标范围：`box = await locator.bounding_box()`。
3.  **系统做手**：将获取到的坐标传入 Python 级驱动库（如 `PyAutoGUI`，或大漠插件 DLL）。由系统级函数执行 `pyautogui.moveTo(x, y)` 和 `pyautogui.click()`。
4.  **真实键盘击键**：输入文本时，系统真实鼠标点出焦点后，调用 `pyautogui.typewrite()` 进行系统底层键盘注入。

**混合效果**：毫无 CDP 点击特征、毫无键盘注入痕迹、省去了传统大漠必须使用的脆弱的“图像找色”逻辑（因为 DOM 定位绝不会因为 UI 改版而错位），防风控能力无限逼近真人。

## 方案四：转换赛道 —— 真机群控与无障碍服务

Web 端风控的难点在于浏览器提供了丰富的 API（Canvas、字体、WebGL、高精度时序）供平台采集指纹。而原生 App 端由于权限限制，指纹采集能力反而较弱。

*   **实现机制**：避开网页端，转移到 App 端。使用多台真实的 Android 手机组建机架，通过 Android 的无障碍服务（AccessibilityService）或者 UiAutomator，直接在真正的社交媒体 App 上点击发布。
*   **优势**：**纯天然物理环境**。网络走真实运营商，设备是真实手机。
*   **劣势**：**沉重的硬件与运维成本**。需要真机采购、机架搭建，解决电池发热、网络中转，以及音视频等大文件向每一台实体手机的下发同步问题。

---

> **总结论**：当前在不大幅颠覆系统架构的情况下，要提升防风控等级：
> 1. **低成本路线**：可以尝试引入 `Patchright`（抹除 CDP 痕迹）或混合 `Playwright + Extension` 模式。
> 2. **最高安全性路线**：利用当前项目单线程发布的特性，大力推进 **“Playwright 寻址 + PyAutoGUI/大漠 物理按键”** 的混合落地。这将在开发成本极低的情况下，提供防风控领域的终极防御。
