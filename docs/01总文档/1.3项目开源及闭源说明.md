## 一、总体策略（一句话说明）

本项目采用 **“开源版公开源码 + 闭源版仅发布编译产物”** 的双轨策略：
- **开源版**：源码公开到 GitHub 与 Gitee，方便用户二次开发
- **闭源版**：闭源源码**不上传任何公开仓库**，仅在本地/内部环境维护；对外仅在 GitHub/Gitee Release 提供可执行安装包

## 二、三个发行版本（用户能拿到什么）

### 2.0 许可证口径
- **开源版（Community / OSS）**：本项目采用 **PolyForm Noncommercial License 1.0.0**（非商业许可证）。这意味着您可以为学习、个人研究或公益等非商业目的使用和修改源码，但**严禁**将本软件或基于本软件衍生出的产品用于商业牟利（例如二次打包售卖、提供商业SaaS服务等）。详情请参阅仓库根目录的 `LICENSE` 文件。
- **闭源版（Pro / 52pojie 编译产物）**：不提供源码，仅提供可执行安装包；使用条款以安装包内的《用户许可协议/EULA》与官方商业授权公告为准。

### 2.1 开源版（Community / OSS）
**用户获取方式**：GitHub/Gitee 公开仓库拉取源码自行编译运行。  
**用途**：二次开发、学习、社区贡献、基础功能体验。

**开源功能说明与代码目录**：
- **基础底座与 UI**：提供完整的前端渲染引擎与通用模块（位于 `src/ui/`、`src/infrastructure/`）。
- **社区平台插件**：支持**抖音（douyin）、快手（kuaishou）**平台账号的绑定以及基本的单次视频/图文发布功能（位于 `src/plugins/community/`）。
- **独立环境**：支持账号隔离的工作区机制，不强制依赖云端鉴权即可运行上述社区能力。

**开源版限制原则**：
- 代码中不包含“媒小宝账号登录与会员权限体系”的实现细节。

### 2.2 闭源版（Pro / Full，当前为免费试用）
**用户获取方式**：在 GitHub/Gitee 的 Release 下载编译产物（安装包）。  
**用途**：完整体验当前软件所有进阶功能与全平台矩阵能力（以闭源版为准）。

**闭源核心进阶功能与代码目录**：
- **高密商业平台矩阵**：除开源社区平台外，额外支持**视频号、小红书、哔哩哔哩、微博、今日头条、百家号、多多视频、企鹅号**等 8 个高防护平台的自动化发布（位于 `src/plugins/pro/`）。
- **批量与全自动化能力**：支持多账号、多平台并发编排的**批量定时发布**系统（位于 `src/pro_features/batch/`）。
- **数据与互动**：支持跨平台的数据大屏统计与评论管理互动中心（位于 `src/pro_features/data_center/`、`src/pro_features/interaction/`）。
- **云端账号鉴权**：商业化的核心授权订阅、用量拦截与会话管控系统（实现位于 `src/proprietary/auth/`、`src/proprietary/subscription/`；开源仓仅见 `src/services/auth/`、`src/services/subscription/` 包装层）。

**当前授权方式（试用策略）**：
- 用户完成 **注册并登录媒小宝账号**
- 按引导 **关注功能号**（由服务端完成校验）
- 校验通过后获得 **全部权限**（试用期策略如有变更，以软件内提示与公告为准）

> 说明：闭源版的“权限开通逻辑”属于商业规则，不在开源仓库公开。

### 2.3 闭源版：吾爱特别版（52pojie / Offline Full，可选）
**用户获取方式**：在指定渠道下载闭源版编译产物。  
**用途**：离线/弱网环境下的本地全权限体验（不依赖云端授权服务）。

### 3.1 双仓库协作（本地一份代码，两个远程）

项目采用 **「私有主仓 + 公开开源镜像」**，开发者只维护**一个本地文件夹**，对应两个 Git 远程：

| 远程名 | 仓库 | 可见性 | 内容 |
|--------|------|--------|------|
| `origin` | `wemedia-baby-Pro` | **私有** | 完整源码：开源骨架 + 闭源实现 + 内部文档 |
| `public` | `wemedia-baby` | **公开** | 仅开源快照（由脚本生成，不含闭源目录） |

**日常开发（推私有主仓）**：

```powershell
git add .
git commit -m "提交说明"
git push origin main
```

也可使用 VS Code / Cursor **源代码管理器** 的「提交 + 同步更改」，默认推送到 `origin`（私有仓）。

**更新公开开源仓（勿直接 `git push public main`）**：

1. 确保 `main` 已提交且工作区干净（`git status` 无未提交文件）；
2. 双击 `scripts/git/publish_oss_to_public.bat`，或执行 `.\scripts\git\publish_oss_to_public.ps1`；
3. 仅试跑、不推送：加参数 `-DryRun`。

脚本从**本地 `main`** 生成 `oss-release` 快照（不是从 GitHub 私有仓拉取再推），在临时 worktree 中去掉闭源路径后推送到 `public` 的 `main`。详细说明见 `docs/internal/GIT_DUAL_REPO.md`。

**建议安装一次防误推钩子**（每台电脑、每个克隆执行一次）：

```powershell
.\scripts\git\install_git_hooks.ps1
```

安装后，手动 `git push public` 会被拒绝；仅同步脚本在推送时临时放行。

**密钥与本地配置**（两个仓库均不得提交）：`config/auth_config.json`、`config/dist_mode.json`、`.env` 等，仅保留 `*.example` 示例。

### 3.2 目录与仓库内容对照

**私有主仓 `wemedia-baby-Pro` 包含（完整版）**：

| 路径 | 说明 |
|------|------|
| `src/plugins/community/` | 开源社区平台插件（抖音、快手等） |
| `src/plugins/pro/` | 闭源商业平台插件（视频号、小红书等） |
| `src/pro_features/` | 闭源进阶功能（批量发布、数据中心、互动等） |
| `src/proprietary/` | 闭源核心实现（登录、订阅、素材库/个人中心等真实 UI） |
| `src/services/auth/`、`src/services/subscription/` | **开源包装层**（优先 `import` 闭源实现，缺失时降级） |
| `docs/` | 内部技术文档（含本文档） |

**公开开源仓 `wemedia-baby` 仅包含（由同步脚本保留）**：

- 开源 core：`src/ui/`、`src/infrastructure/`、发布流水线框架、插件框架接口等；
- Community 插件：`src/plugins/community/`；
- 上述路径下的 **包装层**（`src/services/auth/` 等，无 `src/proprietary/` 时自动降级）；
- 面向社区的 README、LICENSE、贡献说明等。

**公开仓严禁出现**（脚本推送前会校验并排除）：

- `src/proprietary/`
- `src/plugins/pro/`
- `src/pro_features/`
- `docs/`（内部文档，不对外同步；对外说明以 README、CHANGELOG 等为准）
- 真实密钥与内部配置（见 3.1 节）

> 说明：早期版本曾将闭源目录写入 `.gitignore` 仅本地存在；自 v1.4.0 起改为 **私有仓纳入版本管理、公开仓由脚本剥离**，避免维护两份本地文件夹。

### 3.3 闭源编译产物（Release 附件）
公开仓库的 Release 可以同时提供闭源版下载，但必须遵循：
- **只发布安装包/可执行产物**，不上传闭源源码
- 不发布调试符号/未混淆中间产物（例如 `.pdb`、未压缩的中间目录等）
- 同步发布校验信息（建议提供 SHA256）与变更说明

> 备注：`version.json` 是版本信息权威来源；若存在软件内“检查更新”，其对比源也应以 Release 与 `version.json` 的公开信息为准。

## 四、功能边界与隔离原则（怎么保证开源不影响闭源）

### 4.1 开源/闭源边界（建议按模块隔离）
- **必须闭源**：
  - 媒小宝账号登录与会话（token/记住登录/挤下线等）
  - 会员权限与额度（订阅、试用次数、日发布上限、Pro 平台权限）
  - Pro 平台插件实现与商业化能力
- **可以开源**：
  - UI 框架与通用组件（不绑定账号体系）
  - 发布流水线框架（不内置强制会员校验）
  - 插件框架接口与社区平台插件（按业务安全评估）

### 4.2 推荐实现方式：包装层 + 闭源目录（当前落地方式）

开源仓库保留 **包装模块**（如 `src/services/auth/auth_config.py`），内部优先加载 `src/proprietary/` 中的真实实现；若闭源目录不存在（公开仓克隆场景），则回退为 OSS 默认行为（例如不启用云端认证），**不因 ImportError 崩溃**。

闭源真实实现集中在：

- `src/proprietary/`：登录、订阅、个人中心、素材库等；
- `src/plugins/pro/`、`src/pro_features/`：Pro 平台与进阶业务能力。

长期也可继续演进为更抽象的 `AuthProvider` / `PermissionProvider` 接口，但对外口径以「公开仓仅见包装层 + 社区插件」为准。

### 4.3 Feature Flag（用于打包差异，但不是安全边界）
项目已有 `config/feature_flags.py` 控制 Community/Pro 功能差异。需要强调：
- Feature Flag 适合做“功能开关/编译差异”，但**不能当作闭源安全边界**
- 真正的商业保护仍需“源码不公开 + 闭源打包（Nuitka）+ 服务端授权校验”

## 五、授权与隐私说明（对外必须说清楚）

### 5.1 闭源版联网行为（最小化原则）
闭源版为实现注册登录、关注校验、权限开通，需进行必要联网请求。对外口径建议遵循：
- 仅为授权与必要业务请求联网
- 用户素材内容仅在用户主动发布到平台时才会发生上传
- Cookie/数据库等敏感数据仅存储本地（项目已将 `data/` 加入忽略规则）

> 如后续接入遥测/崩溃上报，应在隐私说明中明确告知并提供关闭选项。

## 六、发布流程建议（避免“发错包/发错仓”）

### 6.1 日常源码备份（完整版 → 私有仓）
- 本地改代码 → `git commit` → `git push origin main`（或 IDE 源代码管理器同步）
- 确认未提交 `auth_config.json`、`.env` 等敏感文件

### 6.2 开源版源码发布（公开仓）
- 在私有仓提交已稳定的前提下，运行 `scripts/git/publish_oss_to_public.bat`
- 到 `https://github.com/chitang818/wemedia-baby` 核对：**无** `src/proprietary/`、`src/plugins/pro/` 等目录
- 需要 Gitee 镜像时，由 Gitee 从 GitHub 公开仓同步（或按既有镜像流程）
- 打 Tag / Release（可选）；更新 README：开源版范围、构建方式、贡献方式

### 6.3 闭源版安装包发布
- 本地/内部环境完成构建（建议使用 Nuitka 发布包）
- 上传安装包到 GitHub/Gitee Release
- 同步更新 `version.json` 与更新说明
- 发布后做一次“下载-安装-登录-关注-解锁-发布冒烟”回归

---

## 七、安全合规要求（必须长期遵守）

### 7.1 仓库安全
- 严禁将闭源源码推送至公开仓：禁止 `git push public main`，必须使用 `publish_oss_to_public` 脚本
- 建议执行 `scripts/git/install_git_hooks.ps1`，降低误推 `public` 的概率
- 严禁在**任一**仓库提交真实密钥、内部域名、测试账号等敏感信息
- 对外发布的安装包建议进行数字签名（降低被篡改风险）

### 7.2 构建安全
- 发布包优先使用 Nuitka（提高反编译门槛）
- Release 附件建议提供校验值（SHA256）供用户核验
