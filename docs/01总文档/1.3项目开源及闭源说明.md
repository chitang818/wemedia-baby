## 一、总体策略（一句话说明）

本项目采用 **“开源版公开源码 + 闭源版仅发布编译产物”** 的双轨策略：
- **开源版**：源码公开到 GitHub 与 Gitee，方便用户二次开发
- **闭源版**：闭源源码**不上传任何公开仓库**，仅在本地/内部环境维护；对外仅在 GitHub/Gitee Release 提供可执行安装包

---

## 二、三个发行版本（用户能拿到什么）

### 2.0 许可证口径（建议在开源前统一）
- **开源版（Community / OSS）**：使用开源许可证（例如 AGPLv3/MIT/Apache-2.0 等，按最终选择为准）；仓库根目录需放置 `LICENSE` 并在 README 明确说明。
- **闭源版（Pro / 52pojie 编译产物）**：不提供源码，仅提供可执行安装包；使用条款以安装包内的《用户许可协议/EULA》与公告为准。

### 2.1 开源版（Community / OSS）
**用户获取方式**：GitHub/Gitee 公开仓库拉取源码自行编译运行。  
**用途**：二次开发、学习、社区贡献、基础功能体验。

**开源版原则**：
- 代码中不包含“媒小宝账号登录与会员权限体系”的实现细节
- 开源版可在没有云端授权服务的情况下运行其开放功能（不强依赖登录/会员校验）

### 2.2 闭源版（Pro / Full，当前为免费试用）
**用户获取方式**：在 GitHub/Gitee 的 Release 下载编译产物（安装包）。  
**用途**：完整体验当前软件所有功能（以闭源版为准）。

**当前授权方式（试用策略）**：
- 用户完成 **注册并登录媒小宝账号**
- 按引导 **关注功能号**（由服务端完成校验）
- 校验通过后获得 **全部权限**（试用期策略如有变更，以软件内提示与公告为准）

> 说明：闭源版的“权限开通逻辑”属于商业规则，不在开源仓库公开。

### 2.3 闭源版：吾爱特别版（52pojie / Offline Full，可选）
**用户获取方式**：在指定渠道下载闭源版编译产物。  
**用途**：离线/弱网环境下的本地全权限体验（不依赖云端授权服务）。

- **闭源版安装包下载（GitHub Releases）**：`<待填写：GitHub Release 页面>`
- **闭源版安装包下载（Gitee Releases）**：`<待填写：Gitee Release 页面>`

### 3.1 开源源码仓库（公开）
建议保持两端一致（GitHub / Gitee 同步镜像），仅包含：
- 开源 core（基础 UI、通用发布流水线框架、插件框架接口等）
- Community 插件（例如 `src/plugins/community/`）
- 开源版文档、开发指南、贡献指南、Issue 模板

**严禁包含**（避免“闭源倒灌”）：
- 媒小宝账号登录与鉴权实现：`src/services/auth/`（或其等效实现）
- 订阅/会员/额度校验实现：`src/services/subscription/`
- 发布前服务端校验的具体实现细节（接口字段、错误码、签名规则等）
- 任何闭源平台插件实现（例如 `src/plugins/pro/`）
- 可能泄露内部能力的配置与密钥（包括但不限于：固定域名、后台管理口、内部测试账号等）

### 3.2 闭源编译产物（Release 附件）
公开仓库的 Release 可以同时提供闭源版下载，但必须遵循：
- **只发布安装包/可执行产物**，不上传闭源源码
- 不发布调试符号/未混淆中间产物（例如 `.pdb`、未压缩的中间目录等）
- 同步发布校验信息（建议提供 SHA256）与变更说明

> 备注：`version.json` 是版本信息权威来源；若存在软件内“检查更新”，其对比源也应以 Release 与 `version.json` 的公开信息为准。

## 四、功能边界与隔离原则（怎么保证开源不影响闭源）

### 4.1 开源/闭源边界（建议按模块隔离）
- **必须闭源**：
  - 媒小宝账号登录与会话（token/记住登录/挤下线等）
  - 会员权限与额度（订阅、试用次数、日发布上限、Pro 平台权限）
  - Pro 平台插件实现与商业化能力
- **可以开源**：
  - UI 框架与通用组件（不绑定账号体系）
  - 发布流水线框架（不内置强制会员校验）
  - 插件框架接口与社区平台插件（按业务安全评估）

### 4.2 推荐实现方式：接口化（长期维护成本最低）
开源 core 只依赖抽象接口（示例名）：
- `AuthProvider`：是否登录、获取用户信息、触发登录 UI
- `PermissionProvider`：发布许可、Pro 能力、额度校验

开源版提供“默认实现”（无登录/无会员/本地免费），闭源版提供“真实实现”（云端账号与权限校验）。  
这样可避免开源代码中出现对闭源模块的硬依赖 import。

### 4.3 Feature Flag（用于打包差异，但不是安全边界）
项目已有 `config/feature_flags.py` 控制 Community/Pro 功能差异。需要强调：
- Feature Flag 适合做“功能开关/编译差异”，但**不能当作闭源安全边界**
- 真正的商业保护仍需“源码不公开 + 闭源打包（Nuitka）+ 服务端授权校验”

## 五、授权与隐私说明（对外必须说清楚）

### 5.1 闭源版联网行为（最小化原则）
闭源版为实现注册登录、关注校验、权限开通，需进行必要联网请求。对外口径建议遵循：
- 仅为授权与必要业务请求联网
- 用户素材内容仅在用户主动发布到平台时才会发生上传
- Cookie/数据库等敏感数据仅存储本地（项目已将 `data/` 加入忽略规则）

> 如后续接入遥测/崩溃上报，应在隐私说明中明确告知并提供关闭选项。

## 六、发布流程建议（避免“发错包/发错仓”）

### 6.1 开源版发布
- 推送源码到 GitHub/Gitee
- 打 Tag / Release（可选）
- 更新 README：开源版范围、构建方式、贡献方式

### 6.2 闭源版发布
- 本地/内部环境完成构建（建议使用 Nuitka 发布包）
- 上传安装包到 GitHub/Gitee Release
- 同步更新 `version.json` 与更新说明
- 发布后做一次“下载-安装-登录-关注-解锁-发布冒烟”回归

---

## 七、安全合规要求（必须长期遵守）

### 7.1 仓库安全
- 严禁将闭源源码推送至任何公开仓库（含误操作的 Fork/镜像）
- 严禁在开源仓库提交真实密钥、内部域名、测试账号等敏感信息
- 对外发布的安装包建议进行数字签名（降低被篡改风险）

### 7.2 构建安全
- 发布包优先使用 Nuitka（提高反编译门槛）
- Release 附件建议提供校验值（SHA256）供用户核验
