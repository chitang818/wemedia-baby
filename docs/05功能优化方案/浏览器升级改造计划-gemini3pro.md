# 浏览器防风控升级改造计划 (反检测与防限流)

## 1. 背景与当前痛点

随着自媒体平台（抖音、快手、小红书、视频号等）风控技术的升级，它们对自动化发布的打击力度空前加大。小红书等平台会有显性的“使用自动化脚本”弹窗警告，而抖音、视频号等平台可能采用**“暗网检测”机制**：后台默默记录你的异常特征，不直接封号，而是对账号进行隐形降权、限流，导致精心准备的作品“零播放”，这对运营来说是毁灭性的打击。

平台检测的主要方向分为两层：
1. **浏览器底层与协议环境**：是否携带自动化框架特有标识、TLS 握手特征是否异常。
2. **操作行为特征**：鼠标轨迹、点击频率、滚动习惯是否符合人类生物学。

## 2. 当前项目浏览器防风控现状与缺口分析

目前项目已经搭建了一层较好的防护底座：
- 调度真实 Google Chrome，而非测试用的 Chromium。
- **Patchright 底层补丁**：近期已引入 `patchright`，从 CDP 协议底层抹去了原生 Playwright 的暴露特征。
- 区分平台注入最小化隐身脚本，移除了会触发黄色横幅的自动化启动参数。

**但结合 2024-2025 年最新的反爬/反自动化检测技术，目前系统仍存在致命缺口：**

### 缺口一：机械化行为轨迹（最高危）
Playwright 的核心 `.click()`、`.fill()` 方法是瞬间计算坐标并触发原生点击事件的，**完全没有鼠标移动过程**。平台前端的 JS 探针通过监听 `mousemove`、`pointerdown` 等事件，能轻易发现“这台电脑的鼠标是瞬间瞬移的”，这是最容易被识别并导致限流的机器特征。

### 缺口二：原生 Stealth JS 库的老化
依赖 JavaScript 去覆盖 `navigator.webdriver` 或伪装 Canvas 指纹（如项目中的 `stealth.js`）的手段已经逐渐过时。因为通过 `Object.defineProperty` 修改的对象在原型链（Prototype Chain）层面和原生对象有细微区别，高级风控（如 Cloudflare, DataDome）早已能检测到“变量被脚本劫持修改过”的痕迹。

### 缺口三：TLS 指纹与辅助请求不一致
如果项目中使用了传统的 Python 请求库（如 `requests`, `aiohttp`）去辅助下载封面、获取配置等，它们的底层 TLS (JA3) 握手特征与 Chrome 浏览器截然不同。当同一个 IP 同时发出“爬虫特征的握手”和“Chrome 特征的握手”时，极易被标记为机器人中转站。

## 3. 升级改造计划 (分阶段实施方案)

为了最大程度规避账号限流和封禁，提出以下改造方向：

### 阶段一：操作行为的“深度拟人化”重构（短期高优，防限流核心）

1. **引入仿生鼠标轨迹引擎**
   - **方案**：弃用所有框架自带的瞬时 `.click()`。引入基于贝塞尔曲线（Bézier curve）的鼠标轨迹生成算法，模拟人类滑动鼠标时的加速、减速、抖动和过冲现象。
   - **效果**：在平台页面的热力图和事件追踪中，表现为完全符合物理力学的真实用户滑动。

2. **打字与输入行为仿生**
   - **方案**：重写 `page.fill()`。文本输入必须按键分解，每个字符间加入服从正态分布的随机延迟（如 50ms~150ms）。
   - **进阶**：加入 3% 的模拟打错回退率（故意输错一个字母，按 Backspace 删除，再输入正确的），以此骗过输入行为分析器。

3. **仿真自然滚动与阅读停顿**
   - **方案**：替换生硬的 `scrollIntoView`。使用类似鼠标滚轮的步进式滚动（带 easing 缓动效果），并在到达页面底部或特定区域时加入 0.5s - 2s 的阅读停顿。

### 阶段二：底层防线强化与隔离升级（中期实施）

1. **全面依赖 Patchright，精简 JS 层面的显式伪装**
   - **方案**：高级风控时代，“不做伪装就是最好的伪装”。未来的趋势是依靠 `Patchright` 在 C++ 源码层面上让浏览器变得干净，从而撤销大部分使用 JS 注入的指纹篡改（如 `stealth.js` 中的部分侵入式修改），防止“因为防风控插件本身的特征”被平台抓包。

2. **网络层 TLS 指纹伪装统一**
   - **方案**：项目中所有的后台辅助网络请求，逐步替换为 `curl_cffi`。该库能够完美模拟 Chrome 120+ 的 TLS 和 HTTP/2 指纹，确保项目对平台发出的每一条请求，在底层网络包分析上都像是来自同一个真实 Chrome。

3. **硬件级指纹浏览器对接考量**
   - **方案**：针对手握几十上百个账号的高频工作室用户，单靠一套指纹容易引起同设备多账号关联。架构上可以考虑预留接口，支持对接市面上成熟的指纹浏览器（如 AdsPower、Hubstudio 的 Local API），将繁重的隔离工作交给专业反指纹引擎，本软件只专注上层业务逻辑流。

### 阶段三：云端代理与环境强绑定（长期实施）

1. **账号 - IP - 时区（Geo-Coherence）的三维固化**
   - 如果用户使用了代理 IP 发送作品，软件需记录并强制绑定该账号对应的地理位置。不仅是网络出口在异地，还需在 CDP 级别把浏览器的时区、`Accept-Language` 头动态同步为与 IP 所在地一致，防止出现“广东 IP 却发着北京时间系统包”的低级风控穿透。

## 结论

本次改造重点将从**“清理框架痕迹”**（第一阶段底层修补，现已初步完成）正式迈向**“行为仿生学”**。
下一步的首要行动应当是在项目中引入一套**鼠标与键盘事件重写的中间件**，接管所有自动化页面的交互动作。这将极大地降低各平台（尤其是隐形限流的抖音等平台）对机器行为的捕捉率，保障资产安全。
