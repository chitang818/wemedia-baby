# 媒小宝分发及打包规划（最新）

> 目标：在**一套产品体系**下，稳定产出三种可分发版本：**开源版（社区）**、**闭源完整版（商业 Pro）**、**闭源吾爱特别版（离线全权限）**。  
> 本文是“版本边界 + 构建产物 + 发布流程 + 风险控制”的落地方案，供后续研发/打包/发版对齐使用。

---

## 1. 三个发行版本定义（你要做的“产品分身”）

### 1.1 开源项目（Community / Open Source）
**定位**：让用户能体验“基础发布流程 + 基础平台能力 + UI 框架”，但不包含商业化能力与账号体系。  

**明确不包含（不开放）**：
- **批量任务**：批量视频任务、批量图文任务
- **资产库**：媒体库（视频/图片/文案）、素材管理增强
- **商业功能**：带货推广、数据中心、评论及私信等互动能力
- **媒小宝账号体系**：个人中心、登录、会员等级/订阅/试用次数、发布额度、服务端授权校验等“权限限制”

**建议保留（开放）**（可作为开源版核心价值）：
- 基础 UI 框架、基础导航/页面容器
- “发布列表/发布流水线”的**通用框架**（不绑定会员校验）
- Community 平台能力（以 `src/plugins/community/` 为主），但要避免包含“商业平台/Pro 插件实现”

> 重要：开源版应做到“即使没有任何云端授权服务，也能正常运行基础功能”，而不是运行时强依赖登录/权限接口。

### 1.2 闭源项目（Pro / Full）
**定位**：当前软件“全功能正式商业版”。  
**包含**：当前软件所有功能（含 Pro 功能页面、平台插件、媒小宝账号登录、订阅权限与额度限制等）。

### 1.3 闭源项目：吾爱特别版（52pojie / Offline Full）
**定位**：在闭源完整版基础上，提供“**离线可用、本地全权限**”体验，用于特定渠道分发。  
**策略**：
- 个人中心提供**本地内置账号**（或本地授权文件）
- 禁用云端依赖：不要求云端登录、不要求云端 publish_check 校验
- 全权限放行：会员等级/额度/试用次数等限制在该版本中默认放行

## 2. 代码边界与目录拆分建议（开源/闭源怎么“干净分离”）

### 2.1 必须闭源的代码块（建议从开源仓库剥离）
以下模块属于“账号体系/权限限制/商业规则”，建议 **不出现在开源仓库**：
- `src/services/auth/`：媒小宝账号登录、token、记住登录、云端接口客户端等
- `src/services/subscription/`：订阅/权限控制（会员等级、试用次数、额度）
- 发布前强制校验逻辑：例如发布流水线中的 `permission_check_filter*`（若它直接依赖上面两块）
- “个人中心”相关 UI 页面与数据结构（如果与账号体系强耦合）

> 原则：开源仓库里不应包含可以直接复用的授权/会员接口细节（字段、错误码、URL、校验规则），否则等同于“把商业规则公开”。

### 2.2 可以开源的代码块（建议保留在开源仓库）
- 基础 UI 框架与通用组件（不绑定账号体系）
- 发布流水线框架与通用上下文（不做硬编码权限拦截）
- 插件框架接口（例如登录插件接口/发布插件接口的“抽象定义”）
- Community 插件（如仅包含公开平台能力且不涉及商业秘密）

### 2.3 推荐的“分层”方式（最利于长期维护）
不建议靠“手工删文件”发开源包；建议通过“接口隔离 + 可插拔实现”长期维护：
- **开源 core**：只依赖 `AuthProvider` / `PermissionProvider` 这类抽象接口（默认实现为“无登录/无权限校验/本地免费模式”）
- **闭源 pro/auth 包**：提供真实实现（对接现有 `src/services/auth/*`、`src/services/subscription/*`）

这样可以做到：
- 开源版：没有闭源包也能跑（功能自然受限）
- 商业版：附带闭源包后自动增强（启用登录与权限限制）

## 3. 构建与打包策略（从“源码”到“安装包”）

> 本项目已有成熟的“双轨制打包”：**快速构建（PyInstaller）** 与 **安全构建（Nuitka）**，最终都用 **Inno Setup** 产出安装包。  
> 细节可参考：`docs/01总文档/1.4软件打包实施方案.md`

### 3.1 打包方式（开发期 vs 发布期）
- **迭代期（开发/测试）**：PyInstaller + Inno Setup  
  - 优点：构建快、调试友好  
  - 产物：`dist/fast/` 与 `dist/installers/`
- **发布期（对外交付）**：Nuitka + Inno Setup  
  - 优点：安全性高、启动更快、反编译门槛高  
  - 产物：`dist/secure/` 与 `dist/installers/`

### 3.2 构建矩阵（一次发版同时产出 3 个版本）
已落地一个“发行模式”变量（环境变量 + 随包固化文件）：
- `APP_DIST_MODE=OSS`：开源版
- `APP_DIST_MODE=PRO`：闭源完整版
- `APP_DIST_MODE=52POJIE`：闭源吾爱特别版

并在安装包内随包携带：`config/dist_mode.json`（运行时未设置环境变量时作为兜底默认值）。

并结合现有 Feature Flag（见 `config/feature_flags.py`）实现：
- **OSS**：禁用所有 Pro 页面/能力 + 禁用 `user_auth/subscription`（不出现个人中心与权限限制）
- **PRO**：全部功能启用（正常登录与权限限制）
- **52POJIE**：功能全开，但“账号体系走本地注入/本地授权”，云端校验短路或禁用

> 核心要求：三个版本应尽量“同一套打包脚本”完成，减少维护成本与人为失误。

### 3.3 安装包命名与产物规范（建议）
安装包统一输出到 `dist/installers/`，文件名建议包含：
- 产品名 + 版本号 + 构建类型 + 发行模式  

示例（仅示意）：  
- `WeMediaBaby_Setup_Fast_OSS_vX.Y.Z.exe`  
- `WeMediaBaby_Setup_Secure_PRO_vX.Y.Z.exe`  
- `WeMediaBaby_Setup_Secure_52POJIE_vX.Y.Z.exe`

> 发版时建议使用一键脚本：`scripts/release/build_release_matrix.ps1`，自动产出上述三套安装包。

## 4. 分发策略（你要“怎么发出去”）

### 4.1 开源版分发（建议）
- **代码仓库**：独立开源仓库（只含 core + community 插件）
- **Release 产物**：给普通用户下载 Windows 安装包（降低使用门槛）
- **许可证**：按你计划采用的开源协议执行，并在 README 与安装包内保持一致口径

### 4.2 Pro 商业版分发（建议）
- 渠道：官网/私域/授权客户群
- 交付：安装包 + 授权方式（云端账号/许可证文件）
- 支持：自动更新策略、回滚策略、故障定位（闭源可包含更多诊断）

### 4.3 吾爱特别版分发（建议）
- 渠道：特定论坛/特定发布贴
- 原则：离线可用、去云端依赖、避免联网误触发（尤其是授权校验、同步、遥测）
- 风险：二次打包与篡改风险更高，建议仍保持一定的混淆/签名策略

## 5. 升级、回滚与兼容性（避免用户“更新后崩”）

### 5.1 版本号权威来源
- 统一以根目录 `version.json` 为准（构建脚本会读取）

### 5.2 数据兼容策略（建议）
- 本地 SQLite 数据结构升级需提供“向前兼容/迁移”策略
- OSS/PRO/52POJIE 三个版本升级时，避免出现“数据库字段缺失导致无法启动”

### 5.3 回滚策略（建议）
- 安装包层面：允许卸载后安装旧版
- 运行时层面：关键配置与数据库提供自动备份（回滚时可恢复）

## 6. 风险清单与检查表（发版前必须过一遍）

### 6.1 开源版（OSS）重点风险
- 不应包含：云端授权接口地址、鉴权字段、权限规则细节、内部错误码含义
- 不应强依赖：`src/services/auth/*`、`src/services/subscription/*`
- 开源版启动后不应弹出“必须登录/必须校验会员”才能进入基础功能

### 6.2 Pro 版（PRO）重点风险
- 权限校验链路完整：未登录/过期/超额度应被正确拦截
- 云端不可达时的降级策略要明确（放行/拒绝/提示）

### 6.3 吾爱特别版（52POJIE）重点风险
- 严格控制联网行为：避免误触发云端授权/同步/遥测
- 本地授权注入要稳定：避免某些页面仍调用云端导致卡死或报错
