## 1. 模块概述

**文件路径**：`src/infrastructure/common/post_publish_file_handler.py`

**功能**：在发布列表队列执行完每条任务后，根据用户在「发布设置」中选择的操作模式，对该任务的视频或图文文件执行移动归档或删除。

**设计原则**：
- 文件操作异常不影响发布结果（仅记录日志，不修改任务状态）。
- 支持同一账号组内多个账号共用同一文件时，等全部相关任务成功后再执行一次文件操作，防止提前移走导致后续任务失败。
- 模块无状态，通过调用方传入的 `file_groups` 字典维护分组状态。

## 3. 核心数据结构

### 3.1 FileGroupInfo

```python
@dataclass
class FileGroupInfo:
    file_paths: List[str]         # 实际文件路径列表（图文多图时含多个）
    task_ids: Set[int]            # 该分组内的所有任务 ID
    pending_task_ids: Set[int]    # 尚未完成的任务 ID（初始等于 task_ids）
    has_failed: bool              # 分组内是否已有任务失败
    target_type: str              # "account" 或 "group"
    platform: str                 # 平台 ID（account 类型时用于构造路径）
    platform_username: str        # 账号昵称（account 类型时）
    group_name: str               # 账号组名称（group 类型时）
    file_type: str                # "video" 或 "image"
```

### 3.2 file_groups 字典

`build_file_groups` 的返回值，结构为：

```
{
    "{normalized_file_path}|group:{group_id}": FileGroupInfo,   # 账号组共用
    "{normalized_file_path}|account:{account_id}": FileGroupInfo, # 账号独立
    ...
}
```

`normalized_file_path` = 逗号分隔后各路径排序并小写拼接，用于保证同一组文件路径字符串格式不同时也能匹配到同一个 Key。

## 4. 核心方法说明

### 4.1 `build_file_groups(pending_tasks, account_repo, group_repo)`

**调用时机**：发布队列首次启动（`run_task_items is None` 时），只调用一次。

**算法流程**：

```
第一遍：遍历所有 pending 任务
  → 通过 platform_account_id 查询 AccountRepositoryAsync.find_by_id() 得到 group_id
  → 查询 AccountGroupRepositoryAsync.find_by_id() 得到 group_name

统计计数：Counter{ (normalized_file_path, group_id): 出现次数 }
（group_id=None 的不参与组共用计数）

第二遍：确定每条任务的 scope_key
  → 若 group_id 有效 且 该 (file_path, group_id) 组合出现次数 >= 2
     → target_type="group"，scope_key="group:{group_id}"
  → 否则
     → target_type="account"，scope_key="account:{platform_account_id}"

将相同 group_key 的任务合并进同一个 FileGroupInfo
```

### 4.2 `on_task_success(task_id, task, file_groups, action, user_log)`

**调用时机**：`db_publish.update_status(task_id, 'success', ...)` 执行之后。

**逻辑**：
1. 从所有分组中找到包含 `task_id` 的分组。
2. 将 `task_id` 从 `pending_task_ids` 中移除。
3. 若分组 `has_failed=True` → 跳过（不执行文件操作）。
4. 若 `pending_task_ids` 非空 → 输出「等待中」日志，不操作。
5. 若 `pending_task_ids` 为空且 `has_failed=False` → 调用 `_execute_file_action`。

### 4.3 `on_task_failed(task_id, file_groups)`

**调用时机**：所有标记任务失败的分支（包括信息不完整、账号掉线、账号检测异常、`result.success=False`、`CancelledError`、`Exception` 六条路径）。

**逻辑**：将 `task_id` 从 `pending_task_ids` 移除，并设置 `has_failed=True`，阻止该分组后续任何文件操作。

### 4.4 `_execute_file_action(info, action, user_log)`

**move 模式**：
1. 查 `MaterialLibraryManager.get_root_dir()`，未配置则记警告跳过。
2. 根据 `target_type` 和 `file_type` 调用对应 `*_published_dir` 方法计算目标目录。
3. `mkdir(parents=True, exist_ok=True)` 确保目录存在。
4. 逐文件 `shutil.move(src, dst)`；同名文件追加 `_1`、`_2`…

**delete 模式**：
1. 逐文件 `os.remove(src)`。
2. 不依赖媒体库路径配置。

```
_on_start_publish
    ↓ group_repo 新增
_run_publish_loop(db_publish, account_repo, group_repo, ...)
    ↓ while 前
    post_publish_action = get_post_publish_action()
    file_groups = {}

    ↓ 每次循环
    result = await publish_service.publish_single(...)
    ↓ 成功
    on_task_success(task_id, task, file_groups, action, user_log)
        → pending_task_ids.discard(task_id)
        → if 分组全完成 and not has_failed:
            → _execute_file_action(move/delete)
    ↓ 各失败路径
    on_task_failed(task_id, file_groups)
        → has_failed = True
```

## 9. 边界情况说明

| 场景 | 处理方式 |
|------|----------|
| 媒体库路径未配置（move 模式） | 跳过移动，日志输出警告，不影响发布状态 |
| 源文件不存在 | 跳过操作，记录警告日志 |
| 移动目标目录已有同名文件 | 自动追加 `_1`、`_2`… 后缀 |
| 分组内有任务失败 | `has_failed=True`，整组文件不做任何操作 |
| 队列中途手动停止 | 通过 `CancelledError` 分支触发 `on_task_failed`，文件保留 |
| 图文任务多文件（逗号分隔） | 拆分后逐文件独立操作，单文件失败不影响其他 |
| 账号在组内但仅独用该文件 | 归类为 `account` 类型，发布成功后立即操作，移入账号目录 |
| 源文件不在媒体库目录（如桌面） | move 模式仍按「账号/账号组已发布」目标目录规则移入 |

## 10. 日志输出格式

所有日志通过 `publish.user_log` Logger 输出，在发布日志框可见：

| 情况 | 日志内容 |
|------|---------|
| 等待同组其他任务 | `[文件整理] ⏳ A0001.mp4 还有其他任务未完成，暂不处理` |
| 移动成功 | `[文件整理] ✅ 已将 A0001.mp4 移动至 .../已发布/20260326/` |
| 删除成功 | `[文件整理] ✅ 已删除 A0001.mp4` |
| 未配置媒体库跳过 | `[文件整理] ⚠️ 未配置媒体库路径，跳过移动操作` |
| 源文件不存在 | `[文件整理] ⚠️ 源文件不存在，跳过移动：<路径>` |
| 操作异常 | `[文件整理] ⚠️ 文件操作失败（不影响发布结果）：<错误信息>` |
