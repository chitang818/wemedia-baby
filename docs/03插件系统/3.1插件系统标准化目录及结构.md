## 1. 标准化目录结构

每个平台插件必须遵循以下目录结构。以 `<platform_id>` 表示平台标识（如 `douyin`、`kuaishou`）。

```text
src/plugins/<community|pro>/<platform_id>/
├── __init__.py              # 包初始化（可为空或导出关键类）
├── config.json              # 平台元数据与 limits 配置
├── login_plugin.py          # 登录插件（实现 LoginPluginInterface）
├── publish_plugin.py        # 发布插件（实现 PublishPluginInterface）
├── selectors.py             # CSS/XPath 选择器常量（按功能分组）
├── scripts.py               # 注入浏览器的 JavaScript 检测脚本
└── steps/                   # 发布步骤链（步骤数量由平台决定，按序号命名）
    ├── __init__.py           # 步骤说明与对照表
    ├── _base.py              # 步骤基类（可复用 douyin 的 _base.py）
    ├── step_runner.py        # 步骤运行器（按顺序执行各步骤）
    ├── step_01_xxx.py        # 步骤1：由平台定义（如导航首页）
    ├── step_02_xxx.py        # 步骤2：由平台定义（如进入发布页）
    ├── step_03_xxx.py        # 步骤3：由平台定义（如上传文件）
    ├── ...                   # 更多步骤（数量不限，按平台实际需要）
    └── step_NN_submit.py     # 最后一步：点击发布并验证结果
```

### 1.1 各文件职责

| 文件                | 必需 | 职责                                                                                                              |
| ------------------- | ---- | ----------------------------------------------------------------------------------------------------------------- |
| `config.json`       | ✅   | 平台元数据（`platform_id`、`platform_name`、`login_url`、`cookie_domain`、`content_types`）+ 字数限制（`limits`） |
| `login_plugin.py`   | ✅   | 实现 `LoginPluginInterface`，负责登录检测、用户信息提取、HTTP Cookie 验证                                         |
| `publish_plugin.py` | ✅   | 实现 `PublishPluginInterface`，负责组装步骤链并交给 StepRunner 执行                                               |
| `selectors.py`      | ✅   | 集中管理所有 CSS 选择器，按 `LOGIN`、`HOME`、`PUBLISH`、`SECURITY`、`VERIFY`、`SETTINGS` 等分组                   |
| `scripts.py`        | 可选 | 需要注入浏览器执行的 JavaScript（如登录态检测脚本）                                                               |
| `steps/`            | ✅   | 发布步骤链，每个步骤一个文件，由 `step_runner.py` 顺序执行                                                        |

## 2. config.json 标准格式

```json
{
  "platform_id": "<platform_id>",
  "platform_name": "<平台中文名>",
  "login_url": "<创作者中心URL>",
  "cookie_domain": ".<platform>.com",
  "content_types": ["video", "image"],
  "limits": {
    "title_max_length": 30,
    "description_max_length": 1000,
    "max_topics": 5
  }
}
```

此外，平台级扩展配置（如 `anti_risk` 防风控参数）放在 `config/platforms/<platform_id>.json`（项目根目录），由发布插件在 `publish()` 入口读取。

## 3. 登录插件接口规范

继承 `LoginPluginInterface`（`src/plugins/core/interfaces/login_plugin.py`）。

### 3.1 必须实现的属性和方法

```python
class <Platform>LoginPlugin(LoginPluginInterface):

    @property
    def platform_id(self) -> str:
        """平台标识，如 'douyin'"""

    @property
    def platform_name(self) -> str:
        """平台显示名称，如 '抖音'"""

    @property
    def login_url(self) -> str:
        """创作者中心登录页 URL"""

    async def check_login_status(self, context) -> bool:
        """在浏览器页面环境中检测是否已登录
        参数 context: Playwright BrowserContext
        返回: True=已登录, False=未登录
        """

    async def extract_user_info(self, context) -> LoginResult:
        """提取用户信息（昵称、Cookies 等）
        返回: LoginResult(success, cookies, nickname, error_message)
        """

    async def verify_cookie_http(self, session, cookies, user_agent=None) -> LoginResult:
        """通过纯 HTTP 请求验证 Cookie 有效性（不启动浏览器）
        参数 session: aiohttp.ClientSession
        注：主程序统一通过 verify_account_status 入口验证，其默认实现会调用本方法。
        """
```

### 3.2 验证入口说明

- **统一入口**：主程序使用 `verify_account_status(context: AccountVerificationContext) -> LoginResult` 进行账号验证（含 HTTP 静默验证、Headless 等）。  
- **默认行为**：基类 `verify_account_status` 会从 `context` 取出 `http_session`、`cookies`、`user_agent` 并调用 `verify_cookie_http(session, cookies, user_agent)`。  
- **子类**：必须实现 `verify_cookie_http`；若需自定义验证逻辑（如走 Headless），可覆盖 `verify_account_status`。

```python
# AccountVerificationContext（供 verify_account_status 使用）
@dataclass
class AccountVerificationContext:
    account_id: int
    account_name: str
    platform: str
    cookies: Dict[str, str]
    user_agent: Optional[str] = None
    http_session: Optional[object] = None   # aiohttp.ClientSession
    service_locator: Optional[object] = None
```

### 3.3 可选覆盖的方法

| 方法                               | 默认行为                         | 说明                           |
| ---------------------------------- | -------------------------------- | ------------------------------ |
| `cookie_domain`                    | `.{platform_id}.com`             | Cookie 域名，特殊域名时覆盖    |
| `check_url`                        | 同 `login_url`                   | HTTP 验证使用的 URL            |
| `verify_account_status(context)`   | 调用 `verify_cookie_http`        | 统一验证入口，可实现更复杂逻辑 |
| `wait_for_login(context, timeout)` | 每 3 秒轮询 `check_login_status` | 等待用户完成登录               |

### 3.4 LoginResult 数据结构

```python
@dataclass
class LoginResult:
    success: bool
    cookies: Optional[Dict] = None        # 登录成功时的 Cookie 字典
    nickname: Optional[str] = None        # 用户昵称
    avatar_url: Optional[str] = None      # 头像 URL
    user_id: Optional[str] = None         # 用户 ID
    error_message: Optional[str] = None   # 失败/掉线原因（主程序展示用）
    is_valid: bool = True                 # Cookie 是否有效
```

## 4. 发布插件接口规范

继承 `PublishPluginInterface`（`src/plugins/core/interfaces/publish_plugin.py`）。

### 4.1 必须实现的属性和方法

```python
class <Platform>PublishPlugin(PublishPluginInterface):

    @property
    def platform_id(self) -> str:
        """平台标识"""

    def get_form_schema(self, content_type: str = "video") -> List[FormField]:
        """返回发布表单字段定义（供 UI 动态渲染）
        max_length 等从 config 读取
        """

    async def publish(self, context, file_path: str, metadata: Dict[str, Any]) -> PublishResult:
        """执行完整发布流程
        参数 context: Playwright Page（已注入账号 Cookie）
        参数 file_path: 本地视频/图片文件路径
        参数 metadata: {title, description, tags, file_type, cover_type, cover_path, ...}
        返回: PublishResult
        """
```

### 4.2 PublishResult 与 FormField

```python
@dataclass
class PublishResult:
    success: bool
    publish_url: Optional[str] = None      # 发布后的作品链接
    error_message: Optional[str] = None    # 失败原因
    failed_step: Optional[str] = None      # 失败时的步骤名

@dataclass
class FormField:
    name: str              # 字段名（提交数据用）
    label: str             # 显示标签
    field_type: str        # text / textarea / select / checkbox / file / datetime
    required: bool = True
    options: List[Dict] = None    # select 选项 [{'label': 'A', 'value': 'a'}]
    max_length: int = None
    default: Any = None
    placeholder: str = None
```

### 4.3 步骤实现与可信交互

`steps/*.py` 在点击、勾选、时间选择等**会改变页面提交状态**的操作上，应遵循 **[3.2 插件选择器标准化规范 — 第 5.2 节](3.2插件选择器标准化规范.md)**：优先真实指针事件（`Locator.click` / `page.mouse.click` / `human_click`），避免以 `page.evaluate` 内 `node.click()` 或合成 `MouseEvent` 作为主路径，防止「界面已变、内部 model 未变」的假成功。只读探测、滚动、解析仍可使用 `evaluate`。

## 5. 步骤链架构（发布流程核心）

### 5.1 步骤基类

所有发布步骤继承 `BasePublishStep`（`steps/_base.py`），实现 `execute` 方法：

```python
class BasePublishStep(ABC):
    @abstractmethod
    async def execute(self, page: Page, file_path: str, metadata: Dict[str, Any]) -> StepOutcome:
        """
        返回值类型（StepOutcome）：
        - None           → 本步成功，继续下一步
        - PublishResult   → 流程结束（成功或失败）
        - NeedsAction     → 需要补救（如需要封面/补充信息），Runner 处理后重试
        """
```

### 5.1.1 步骤成功与失败的判定规则

**核心原则**：步骤失败 → 终止发布任务；步骤成功 → 进入下一步。

| 场景 | 正确做法 | 说明 |
|------|----------|------|
| 步骤内所有操作均完成 | `return None` | 本步成功，Runner 继续下一步 |
| 功能未配置（如未填商品名称）| `return None`（直接跳过） | 未配置 = 不需要操作，视为成功 |
| 配置了某功能但操作失败 | `return PublishResult(success=False, ...)` | 已配置 = 必须成功，失败则终止 |
| 找不到必要页面元素 | `return PublishResult(success=False, ...)` | 不得静默跳过，应终止并报告原因 |
| 未实现的功能但任务有此配置 | `return PublishResult(success=False, ...)` | 明确报告功能未实现，避免漏填数据 |
| 步骤内关键异常 | `return PublishResult(success=False, ...)` 或 `raise` | Runner 会捕获异常并触发重试/失败 |

**「配置了就必须成功」的约束适用于**：
- 有标题/描述但找不到对应输入框
- 有商品名称但关联商品挂载失败（快手）
- 有购物车/位置/团购/小程序配置但标签填写失败（抖音）
- 有定时时间但定时设置失败

**允许跳过（`return None`）的场景**：
- 对应字段在 metadata 中为空或未配置
- 功能为「可选增强」且明确设计为尽力填写（需在代码注释中声明，并在此文档中列出豁免项）

> **豁免说明**：以下步骤因平台特性或功能未完整实现，暂时保留「有配置亦不报错」的宽松模式，后续随功能完善逐步收紧：
> - （暂无，如有新增请在此处列出并注明原因与计划收紧时间）

### 5.1.2 禁止兜底（No Fallback）原则

> **这是系统最重要的约束之一。** 日志显示成功的发布，必须百分之百对应真实发布成功；如果使用了兜底逻辑，日志可能显示成功但实际未发布成功，在批量发布（100+ 账号）场景中无法人工逐一核对，将造成严重损失。

**禁止使用兜底的具体场景**：

| 反模式（禁止） | 正确做法 |
|----------------|----------|
| 步骤内先尝试主方案，主方案失败后静默切换备用方案继续执行 | 主方案失败 → 立即 `return PublishResult(success=False)` |
| 成功验证遍历多个信号，其中一个模糊信号（如「页面有某文案」）直接视为成功 | 成功判定只接受单一、明确、可辨别的信号（见下） |
| 上传、描述填写失败后静默跳过并继续发布 | 关键步骤失败 → 终止 |
| 发布后通过侧边栏文案或包含过于宽泛条件的 URL 判断成功 | 必须使用精确 URL 路径或特定 Toast 文案 |
| 找不到元素时 `return None` 并 `logger.warning(...)` | 有配置而找不到元素 → 返回失败 |

**成功验证要求（三选一，按优先级）**：
1. **URL 精确跳转**：只接受确定指向作品管理页的 URL 路径（如 `content/manage`、`article/manage`）
2. **特定 Toast 精确匹配**：只接受在 Toast 容器内找到包含精确成功短语（如「发布成功」「内容发布成功」）的元素，且该元素 `is_visible()` 为真
3. **管理页特征元素**：在确认**不在发布编辑页**的前提下，只接受管理页特有元素 `is_visible()` 为真

**填写操作后验证要求**：
- 文本框填写完成后必须通过 `evaluate` 或 `get_attribute` 读回实际内容（`innerText` / `value`）验证非空
- 验证失败 → 返回 `PublishResult(success=False)`，不得改用 JS 直接写入作为兜底方案

**占位步骤豁免**：
- 快手 step_05/07/08/09 等未实现业务的占位步骤，`return None` 是正确行为（非兜底）
- 可选字段未配置时 `return None` 是正确行为

### 5.3 StepRunner 运行器

`step_runner.py` 负责按顺序执行步骤链：

- **正常流程**：逐步执行，每步成功后加入防风控间隔
- **失败重试**：每步最多重试 N 次（默认 3），超限则返回失败
- **NeedsAction 补救**：执行 `action_handlers` 中对应的补救步骤，然后回到 Submit 步骤重试
- **诊断**：失败时自动截图并输出选择器探针命中数

```python
@dataclass
class RunnerConfig:
    max_step_retries: int = 3
    step_retry_delay_seconds: float = 1.5
    max_submit_retries: int = 2
    screenshot_on_error: bool = True
    screenshot_dir: str = "debug/screenshots/<platform_id>"
```

### 5.4 步骤划分原则

每个平台的发布步骤由平台自行定义，**不强制统一为固定步数**。步骤数量和内容取决于平台创作者中心的实际页面流程。

**命名规则**：`step_序号_功能名.py`，如 `step_01_home.py`、`step_02_entry.py`。

**常见步骤类型**（供参考，按需增减）：

| 类型 | 说明                             | 示例                     |
| ---- | -------------------------------- | ------------------------ |
| 导航 | 打开创作者中心，检测登录态和风控 | `step_01_home.py`        |
| 入口 | 点击发布入口，进入对应发布页     | `step_02_entry.py`       |
| 上传 | 上传视频/图文素材                | `step_03_upload.py`      |
| 描述 | 填写标题、描述、话题标签         | `step_04_description.py` |
| 封面 | 设置作品封面（首帧/本地/AI）     | `step_05_cover.py`       |
| 扩展 | 音乐、补充信息等平台特有功能     | `step_06_extra.py`       |
| 设置 | 可见性、定时发布等               | `step_07_settings.py`    |
| 提交 | 点击发布并验证结果               | `step_08_submit.py`      |

> **抖音示例**：8 步（导航→入口→上传→封面/描述→描述/封面→扩展信息→发布设置→提交）。其他平台可能只需 5、6 步，也可能需要 10 步，完全取决于平台页面流程。

> **视频号示例**：11 步（导航→入口→上传→封面→描述→位置→链接→定时→短标题→原创→提交），步骤与 DOM 键名见 [03视频号插件/3.3.4视频号插件DOM对照表](03视频号插件/3.3.4视频号插件DOM对照表.md)。发布页在 `wujie-app` Shadow 内时，步骤实现须与 [3.2 插件选择器标准化规范](3.2插件选择器标准化规范.md) 第 5.1 节一致。

## 6. selectors.py 标准结构

选择器文件应按功能分组，使用列表形式（多候选），便于页面改版时快速更新。

```python
class Selectors:
    # 登录与基础信息
    LOGIN = {
        "QR_CODE": ["<选择器1>", "<选择器2>"],
        "LOGIN_BTN": [...],
    }

    USER_INFO = {
        "NICKNAME": ["<选择器1>", ...],
        "AVATAR": [...],
    }

    REQUIRED_COOKIES = ['sessionid', '...']

    # 首页入口
    HOME = {
        "PUBLISH_VIDEO_BTN": [...],
        "PUBLISH_IMAGE_BTN": [...],
    }

    # 发布页元素
    PUBLISH = {
        "FILE_INPUT": [...],
        "TITLE_INPUT": [...],
        "DESC_EDITOR": [...],
        "COVER_BTN": [...],
        "SUBMIT_BTN": [...],
        # ... 按步骤编号注释
    }

    # 风控与异常
    SECURITY = {
        "RISK_MODAL": [...],
        "PUBLISH_TOAST_ERROR": [...],
    }

    # 结果验证
    VERIFY = {
        "SUCCESS_TOAST": "...",
        "MANAGE_PAGE_INDICATOR": [...],
    }

    # 发布设置
    SETTINGS = {
        "PRIVACY_PUBLIC": [...],
        "PUBLISH_SCHEDULE": [...],
        "SCHEDULE_INPUT": [...],
    }
```

**规范要点**：

- 每个键对应的是**选择器候选列表**（优先使用第一个，后续为兜底）
- 键名要加上**步骤编号注释**，失败时可直接定位
- 与 **[3.2 插件选择器标准化规范](3.2插件选择器标准化规范.md)** 双轨配合：`selectors.py` 管**字符串候选顺序**；`steps/*.py` 管 **scope（弹窗 / Shadow 根）**、**Layer 1（get_by_* 等）优先尝试**以及与 Shadow 一致的**成功/失败探测**。页面改版时往往需**同时**更新 `selectors.py` 与相关步骤，避免「字典已改但步骤仍用未穿透的 `page.locator`」导致误判。
- 各平台 `*DOM对照表.md` 中应维护**代码键名、策略层级（L1/L2/L3）、作用域**（与 3.2 对齐），便于 OpenClaw / Cursor 协同

## 7. 注册新插件

在 `src/plugins/core/plugin_manager.py` 的 `_register_all_plugins()` 方法中添加：

```python
# --- <平台名> ---
try:
    from src.plugins.community.<platform_id>.login_plugin import <Platform>LoginPlugin
    cls._login_plugins["<platform_id>"] = <Platform>LoginPlugin()
except Exception as e:
    logger.error(f"加载<平台名>登录插件失败: {e}", exc_info=True)

try:
    from src.plugins.community.<platform_id>.publish_plugin import <Platform>PublishPlugin
    cls._publish_plugins["<platform_id>"] = <Platform>PublishPlugin()
except Exception as e:
    logger.error(f"加载<平台名>发布插件失败: {e}", exc_info=True)
```

专业版插件路径为 `src.plugins.pro.<platform_id>`，注册方式同上，失败时可用 `logger.debug` 避免未授权环境下刷屏。

## 8. 防风控对接要点

插件在发布步骤中应调用公共防风控模块（`src/infrastructure/anti_risk/`）：

| 能力       | 使用场景              | 调用方式                                                        |
| ---------- | --------------------- | --------------------------------------------------------------- |
| 随机延迟   | 固定等待替代          | `await random_delay(page, metadata, config)`                    |
| 拟人点击   | 关键按钮              | `await human_click(page, selector, metadata, config)`           |
| 拟人输入   | 标题等输入框          | `await human_type_text(page, selector, text, metadata, config)` |
| 步骤间间隔 | StepRunner 每步成功后 | `await step_interval(page, metadata, config)`                   |
| 步骤前浏览 | StepRunner 每步执行前 | `await optional_browse_before_action(page, metadata, config)`   |
| 频繁冷却   | 检测到风控时          | `await cooldown_before_retry(seconds)`                          |

防风控配置从 `config/platforms/<platform_id>.json` 的 `anti_risk` 块读取，由发布插件在 `publish()` 入口写入 `metadata["anti_risk_config"]`。

## 9. 日志规范

| Logger                                  | 用途         | 输出目标         |
| --------------------------------------- | ------------ | ---------------- |
| `logging.getLogger(__name__)`           | 完整技术日志 | 终端 + 日志文件  |
| `logging.getLogger("publish.user_log")` | 发布进度日志 | 主程序发布日志框 |

用户日志格式：`[步骤X/N 步骤名] ▶ 状态`，其中 N 为该平台的总步骤数，如 `[步骤3/8 上传视频/图文] ✓ 完成`。

## 10. AI 编程投喂清单

当使用 AI 编程工具开发新平台插件时，请提供以下材料：

1. **本文档**（标准化目录及接口规范）
2. **[3.2 插件选择器标准化规范](3.2插件选择器标准化规范.md)**（分层选择器、弹窗 scope、Shadow、OpenClaw 报告第 11 节格式）
3. **抖音插件源码**（`src/plugins/community/douyin/`）作为参考实现；若目标平台含 Shadow/微前端，可对照 `src/plugins/pro/wechat_video/`
4. **目标平台的 DOM 材料（二选一或兼有）**：
   - OpenClaw / 人工按 3.2 第 11 节输出的 **《发布操作 DOM 分析报告》**（仓库内可参考 `docs/03插件系统/AI分析报告/` 下样例）
   - 各平台 **`*DOM对照表.md`**（已存在则随改随更）
5. **目标页面是否含 iframe / Shadow DOM**（须在需求中写明，决定 `steps` 主路径是 `locator` 还是 `evaluate` 穿透）
6. **平台配置文件**（`config/platforms/<platform_id>.json`）
7. **核心接口文件**（`src/plugins/core/interfaces/login_plugin.py` 和 `publish_plugin.py`）

**AI 的执行指令模板**：

> 请参考 `src/plugins/community/douyin/` 的实现，为 `<平台名>` 平台创建完整的插件包，存放在 `src/plugins/<community|pro>/<platform_id>/`。
> 必须严格遵循 `docs/03插件系统/3.1插件系统标准化目录及结构.md` 中的标准化目录结构和接口规范，并遵守 `docs/03插件系统/3.2插件选择器标准化规范.md` 中的分层选择器、弹窗作用域与 DOM 对照表同步要求。
> 登录插件继承 `LoginPluginInterface`，发布插件继承 `PublishPluginInterface`，发布流程采用步骤链 + StepRunner 模式。
> **步骤数量和内容由平台实际页面流程决定，不强制统一为 8 步**。抖音的 8 步仅为参考，请根据平台创作者中心的实际操作流程拆分步骤。
> DOM 选择器集中在 `selectors.py`；**按钮/输入的准确度与 Shadow 内校验**在 `steps/*.py` 按 3.2 第 3.1–3.2 节实现。关键操作调用公共防风控模块。
