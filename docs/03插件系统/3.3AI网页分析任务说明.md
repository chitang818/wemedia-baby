## 〇、投喂与阅读顺序（给 AI）

1. **先通读本文档**，建立：要记哪些字段、特殊结构怎么处理、报告长什么样、交付前自检什么。  
2. **再读用户本条对话里的任务说明**（页面 URL、功能名称、操作顺序、测试输入等）——那是**当前唯一的工作范围**，本文档**不会**替你列举「今天要分析哪几步」。  
3. **执行**：打开浏览器 → 按任务说明复现路径 → 边操作边按第三节记录 → 按第四节输出 Markdown 报告 → 第六节自检 → 交付。

**你的输入**：本文档 + 用户的任务说明（可能分多条消息）。  
**你的输出**：一份符合第四节结构的「DOM 分析报告」Markdown，便于后续交给编程助手改选择器/补步骤。  
**边界**：用户未要求的功能不要擅自扩展分析范围；信息不够登录或进页时再简短追问。

## 一、你是谁，你要做什么

你是一个具备浏览器操作能力的 AI 代理（如 OpenClaw、LobsterAI）。

我正在开发一个**自媒体批量发布工具**，通过 Playwright（网页自动化库）控制浏览器，自动完成抖音、快手、视频号等平台的视频/图文发布。

**你的任务是**：

1. **先接收我给出的任务说明**：我会明确说明要分析**哪个页面**、**哪个功能**，并尽量写清该功能的**操作步骤**（先点哪里、再填什么、会弹出什么），以及**可能用到的输入内容**（示例标题、示例文件类型、测试账号可见的选项等）。你据此**自助**打开浏览器、导航到目标页，按步骤自行操作或结合页面结构分析 DOM。
2. **在分析过程中**，用浏览器开发者工具（或你所在工具提供的元素检查能力）记录每一个关键交互元素的 DOM 信息；遇 **iframe、Shadow DOM、contenteditable** 等结构时，按 **§3.4** 增强记录，不可只抄一层外层选择器。
3. 按照本文档第四节规定的格式，生成一份「平台发布操作 DOM 分析报告」。

**协作方式（重要）**：

- 分析是**迭代进行**的：我可能在任意时刻**打断**你的分析，补充背景、纠正理解错误或指明「这一步其实应该先……」。被打断后，请以最新说明为准，修正后续记录与结论，不必从头推翻已确认无误的部分。
- 若我提供的信息不足以安全登录或无法复现路径，再向我**追问**必要信息（例如是否已登录、入口 URL），而不是凭空猜测。

我拿到报告后，会发给 Cursor AI（编程助手），让它更新插件代码里的选择器。

## 二、开始前：我会提供什么；你何时再问我

任务说明一般在**投喂本文档之后**由我在同一会话中发出；也可能与本文档在同一条消息里分前后两段。

**默认由我先说明**（能写多少写多少，不要求一次写全）：

1. **平台与页面**：例如抖音创作者中心、具体 URL 或页面名称（如「视频发布页」）。
2. **要分析的功能**：例如完整发布流程、仅封面设置、仅购物车挂载、定时发布等。
3. **操作步骤**：我认知里的正确顺序（可分段、可后续补充）；若有官方文档或内部说明可一并贴上。
4. **可能用到的输入**：示例文案、是否要上传测试视频/图、需要勾选的选项、易触发弹窗的操作等。
5. **（可选）已知技术特征**：若我了解该平台页面特殊（例如**视频号创作者中心**常用 Shadow DOM、某后台整页在 iframe 内），会提前写明，便于你直接按 **§3.4** 做增强分析。

**你在以下情况可以再问我**（简短追问即可）：

- 缺少登录状态、入口链接或权限，无法进入目标页面。
- 我描述的步骤与当前页面明显不一致，需要我确认以哪一方为准。
- 存在多个同名入口（如多个「发布」），需要我指明业务上要走哪一个。

**不要**把「平台是什么、发视频还是图文」等我已经在任务说明里写清的内容重复问一遍；若信息已足够，直接开始自助分析。

## 三、分析过程中你需要记录什么

### 3.1 每个元素必须记录的信息

对流程中涉及的**每一个关键交互元素**（按钮、输入框、弹窗、文件上传区、单选框等），请记录以下内容：

#### ① 稳定特征（最重要，优先记录）

| 需要记录的内容 | 举例 |
|----------------|------|
| 元素上可见的**文案**（按钮文字、弹窗标题、输入框提示文字） | `发布`、`选择封面`、`请输入标题` |
| 元素的 **HTML 标签类型** | `button`、`input`、`div`、`label` |
| 元素的 **role 属性** | `role="dialog"`、`role="button"` |
| 元素的 **type 属性** | `type="file"`、`type="radio"`、`type="text"` |
| **placeholder** 或 **data-placeholder** 属性的值 | `placeholder="添加作品描述"` |
| **aria-label**、**aria-modal** 等无障碍属性 | `aria-label="关闭"` |
| 工具链分配的临时 **ref 标识**（如 `[ref=e1598]`）| `e1598`（同时标注能否被稳定查询：是/否/未知） |

> **说明**：ref 是浏览器自动化工具的临时引用编号，不是 HTML 里固定存在的属性。记录时请同时说明"是否可以稳定定位到该元素"（填：是 / 否 / 未知）。

#### ② 位置与结构信息

- 元素在页面上的**大致位置**（页面顶部 / 底部 / 弹窗内 / 右侧面板等）
- **父级容器**的稳定特征（父级是否有 `role="dialog"` / 固定 id / 固定文案）
- 是否在**弹窗 / 侧栏 / 下拉框**内（如果是，写出弹窗标题）
- 若元素在 **iframe** 或 **Shadow DOM** 内：除上述描述外，必须按 **§3.4** 补充「所在文档层、宿主链、开放/封闭、自动化穿透建议」

#### ③ class 属性（兜底参考）

- 元素完整的 class 属性值（包括像 `button-dhlUZE` 这样带随机后缀的 class）
- **注意**：这类带随机后缀的 class 在网站改版后会变，只作最后兜底参考

#### ④ 操作结果与交互态变化

- 点击 / 填写该元素后，**页面发生了什么变化**？
  - 弹窗出现了？弹窗关闭了？页面跳转了？出现了什么提示文案？
- **hover / focus 后的 DOM 变化**（有此类交互时必填）：
  - 是否有新元素出现（动态插入 DOM）？还是原本就存在只是被隐藏（`display:none` / `visibility:hidden` / `opacity:0`）？
  - 出现的新元素（如「使用」「添加」按钮）：其标签类型、class、所在父节点是谁（行容器内部 or 面板底部固定区域）？
  - hover 目标元素自身的 class 是否有变化（如增加 `:hover` 或 `active` 状态 class）？
  - 可用 DevTools Elements 面板「Force element state → :hover」验证并截取 hover 前后的 HTML 对比。

#### ⑤ 排他信息（同名控件时必填）

- 如果页面上有**多个文案相同或相近的按钮**（例如多个「确定」「上传」），必须写清：
  - 这个按钮属于哪个区域 / 表单项 / 弹窗？
  - 相邻有什么唯一性的文案 / 标签？
  - 这是第几个同类按钮？

---

### 3.2 弹窗出现时的特别说明

当页面弹出一个弹窗（对话框）时，你需要**同时记录**：

1. **弹窗本身**：弹窗容器的 role 属性、标题文案、class
2. **弹窗内每个按钮**：按钮文案、class、是否是主操作按钮（高亮颜色的那个）
3. **弹窗内的输入框或上传区域**（如果有）
4. **弹窗的关闭方式**：点击 X 按钮 / 点击遮罩层 / 按 Escape 键

---

### 3.3 分析技巧

- 用浏览器开发者工具（按 `F12` → `Elements` 面板）查看元素的 HTML 结构
- 右键点击元素 → 选「检查」，可以快速定位
- **重点关注** `role`、`type`、`placeholder`、`aria-*`、`data-*` 等属性（这些最稳定）
- **固定的中文文案最重要**（业务用语通常不会随改版而变）
- 如果同类按钮有多个，记录它们父级容器的区别

### 3.4 特殊页面结构平台的识别与增强分析（重要）

部分创作者中心（**典型：视频号**）不是「单层 HTML + 普通 div」结构，而是混用 **Shadow DOM（影子 DOM）**、**iframe / 子文档**、**Web Components**、**contenteditable 伪输入** 等。此类页面上，开发者工具里能看到节点，但 Playwright 的常规 `page.locator(...)` 可能**默认穿透不到**封闭树，必须在报告里写清**层级与穿透方式**，否则后续写插件会反复踩坑。

#### 3.4.1 何时必须按「特殊结构」加强分析

满足任一条时，本任务**不能只记表面选择器**，须同步完成 3.4.2 的记录项：

- 在 Elements 面板中，元素路径上出现 **`#shadow-root (open)`** 或 **`#shadow-root (closed)`**。
- 关键操作区落在 **iframe** 内（含嵌套 iframe），或与主文档 **非同源**（无法直接脚本访问时需说明）。
- 输入区是 **`contenteditable="true"`** 的 div/span，而不是标准 `input` / `textarea`。
- 使用自定义标签（如 `xxx-app`、`xxx-editor`）且内部结构在 shadow 内。

若任务说明中已点名平台（如视频号），**默认按可能存在 Shadow DOM / 嵌套处理**，先验证再下结论：确认「无特殊结构」也要在报告中写明「已检查，主文档可直达」。

#### 3.4.2 增强记录项（除 3.1 表格外必填的补充信息）

对**每一个**落在特殊结构内的关键元素，在表格或独立小节中补充：

| 记录项 | 说明 |
|--------|------|
| **所在文档层** | `主文档` / `iframe(名称或 src 特征)` / `Shadow 内` / `Shadow 嵌套（多层需写清顺序）` |
| **Shadow 宿主链** | 从主文档到该元素的 **宿主标签序列**（例：`div#app` → `channels-video-publish` → `#shadow-root` → …）。若 **closed** shadow，说明「无法在 DevTools 展开子树，仅能描述宿主与事件表现」 |
| **开放/封闭** | open 可继续展开记录内部标签；closed 须说明探测手段（如仅能通过宿主暴露的 slot、或键盘/点击行为推断） |
| **与 Playwright 的关系** | 建议写法方向（不必写死项目代码）：如 `locator(...).locator(...)` 链式、`frame_locator`、或「需 `evaluate` 在页内查询 shadowRoot」——并标注**风险**（易碎 / 可维护） |
| **iframe** | iframe 的 `name`、`title`、src 路径特征、是否在 shadow 内；跨域时写明「仅视觉/操作可验证，父页无法读子文档 DOM」 |

#### 3.4.3 视频号等平台分析时的操作要求

- **先画「结构草图」再填表**：用简短层级列表或 ASCII 写清「主文档 → 宿主 → shadow → 子元素」，再对照 3.1 的表格逐元素填写。
- **上传、富文本、定时器等高危步骤**：必须明确该步控件是在主文档还是 shadow / iframe；若同一文案按钮在内外各有一个，**排他信息**写清所属层。
- **弹窗**：说明弹窗根节点在主文档还是某层 shadow 内；关闭按钮若在 closed 树内，单独说明如何稳定触发关闭（Esc、点击遮罩等）。

### 3.5 列表型交互元素的结构分析规范（重要）

当任务涉及「从列表中选择一项」并通过 **hover / 点击行** 触发隐藏按钮（如音乐列表、商品列表、话题列表等），**仅记录叶节点文案和 ref 是不够的**。必须按以下要求额外记录，否则自动化插件无法可靠定位行容器和触发按钮。

#### 3.5.1 何时触发本规范

满足任一条时，必须按本节记录：

- 列表中每一行展示多个子信息（封面图 + 标题 + 副标题 + 时长 + 使用量等）
- 需要 hover 在行上一段时间才能触发操作按钮出现（非常驻显示）
- 操作按钮（如「使用」「添加」「选择」）不是独立的固定按钮，而是随着 hover 目标行动态显示/隐藏

#### 3.5.2 必须记录的内容

**A. 面板 / 抽屉容器（限定查找范围用）**

| 记录项 | 说明 |
|--------|------|
| 容器标签与 class | 整个面板（含搜索框+列表）的根元素，记录标签名和完整 class（哪怕含哈希后缀也写出来） |
| 容器的稳定特征 | 是否有固定 `id`、`role`、`aria-label`，或包含某个唯一文案（如弹窗标题「选择音乐」所在层级） |
| 与页面根元素的层级 | 例：`body > div#DCPF > div[class*='panel']`（不要求精确，大致路径即可） |

**B. 列表容器（`ul` / `div[class*='list']` 等）**

| 记录项 | 说明 |
|--------|------|
| 标签类型与 class | 列表区域根元素（`ul`、`ol`、`div`），完整 class |
| 是否有 `role="listbox"` 等 | 记录 role 属性（无则写「-」） |
| 滚动方式 | 是否可滚动（`overflow:auto/scroll`）、是虚拟滚动还是全量渲染 |

**C. 单行容器（这是 hover 的实际目标）**

| 记录项 | 说明 |
|--------|------|
| 标签类型与完整 class | 单条列表项的根标签（`li`、`div`），class 写完整（含哈希后缀） |
| 是否有 `role` | 如 `role="option"` / `role="listitem"` |
| 行内有哪些子元素 | 逐个列出（封面 `img`、歌名 `span`、时长 `span`、使用量 `span`），各自的标签类型和 class |
| 稳定定位建议 | 给出最短可用的 CSS 选择器，例：`div[class*='music-item']`、`li:has(img)` |

**D. 操作按钮（hover 后出现的「使用」「添加」等）**

| 记录项 | 说明 |
|--------|------|
| hover 前状态 | 按钮在 DOM 中是否存在？是 `display:none`、`visibility:hidden`、`opacity:0`，还是根本不在 DOM 里（动态插入）？ |
| hover 后状态 | 按钮出现的位置：在行容器内部还是面板底部固定区域？标签类型、完整 class、文案 |
| 验证方法 | 可在 DevTools Elements 面板右键该行元素 → Force state → `:hover`，截取 hover 前后 HTML 对比 |
| 所属父节点 | 按钮的直接父节点是哪个标签（是行容器还是单独的操作按钮区） |

#### 3.5.3 记录格式示例（以音乐列表为例）

```markdown
#### 面板容器
- 标签：`div`，class：`music-panel-XxYzAb`
- 稳定特征：包含文案「选择音乐」的标题 `div` 所在第 4 层父容器；内部有 `input[placeholder='搜索音乐']`
- 与根元素路径：`div#DCPF > div.content-xxx > div.music-panel-XxYzAb`

#### 列表容器
- 标签：`ul`，class：`music-list-QwErTy`，无 role 属性
- 滚动：可滚动（overflow:scroll），全量渲染

#### 单行容器（hover 目标）
- 标签：`li`，class：`music-item-AbCdEf`，无 role 属性
- 行内子元素：
  - 封面图：`img`，class：`cover-img-ZzZz`
  - 歌名：`span`，class：`title-OwOwOw`
  - 歌手：`span`，class：`artist-KkKk`
  - 时长：`span`，class：`duration-TtTt`，文案格式：`00:48`
  - 使用量：`span`，class：`usage-UuUu`，文案格式：`65.7万人使用`
- 稳定选择器建议：`li[class*='music-item']`（最短）或 `ul[class*='music-list'] li:has(img)`

#### 操作按钮（hover 后）
- hover 前：存在于 DOM 中，但 `display:none`（或：不存在，hover 时动态插入）
- hover 后：出现在行容器 `li.music-item` 内部右侧，标签 `button`，class：`use-btn-WwWw`，文案「使用」
- 父节点：`li.music-item-AbCdEf`（行内，不是面板底部）
```

## 页面结构与技术特征（特殊结构平台必填；否则写「无：已检查主文档可直达关键控件」）

> 视频号等创作者中心常见 Shadow DOM / iframe；本节不可省略或仅写「无」而不说明检查过程。

### 结构概要

- 是否存在 **iframe**：（是/否；若是有几个、嵌套关系、特征）
- 是否存在 **Shadow DOM**：（是/否；开放 open / 封闭 closed / 混合）

### 4.3 「建议 Playwright API」一列怎么填

请按以下优先级给出建议（从稳定到脆弱）：

| 优先级 | 写法示例 | 何时用 |
|--------|----------|--------|
| **最优先** | `get_by_role('button', name='发布')` | 按钮有可见文案 |
| **次优先** | `get_by_placeholder('请输入标题')` | 输入框有 placeholder |
| **次优先** | `get_by_label('发布时间')` | 表单项有 label |
| **属性选择器** | `input[type='file']` | 文件上传框 |
| **文案属性** | `[data-placeholder='添加描述']` | 富文本编辑区 |
| **最后兜底** | `.button-dhlUZE` | 上面都没有时才用，注明「易碎」 |

**特殊结构补充**（Shadow DOM / iframe 内元素）：在「建议 Playwright API」中优先写清**作用域**（如在 `frame_locator` 之后、`宿主.locator` 链之后）；若标准 API 不可靠，可写「建议在 shadow 宿主上链式 locator」或「需页内 `evaluate` 查询 shadowRoot」，并标注**易碎**或**需封装**。

### 4.4 常见创作者后台技术背景（参考用，不是任务列表）

以下仅供你在遇到对应平台时**快速预判页面形态**；**仍以当前任务说明为准**，不要因下表去分析用户未要求的功能。

| 平台（常见） | 页面形态要点 | 对记录/自动化的影响 |
|--------------|--------------|---------------------|
| **抖音创作者中心** | 多为普通 DOM；常用 Semi Design；不少控件 class 带随机哈希 | **优先**稳定文案、`role`、`placeholder`、`data-*`；哈希 class 只作兜底并标「易碎」 |
| **快手创作者中心** | 多为 React + Ant Design；下拉/日期等浮层常见；部分场景控件可能在 **子 Frame** | 注意 `ant-select-dropdown`、`.ant-picker-dropdown` 等**可见/隐藏**状态；关键按钮若在 frame 内须在报告中写明 frame 特征 |
| **视频号创作者中心** | 常见 **wujie 微前端** + **open Shadow DOM**；部分交互需 **真实鼠标坐标** 或 **页内 evaluate** 才可靠 | **必须**按 §3.4 写「页面结构与技术特征」节；Shadow 内元素逐项写宿主链与穿透建议；勿假设 `page.locator` 能穿透 shadow |

若任务涉及视频号或用户声明存在 Shadow / iframe，报告中「页面结构与技术特征」**不可省略**；若已检查确认无特殊隔离，写明检查结论即可。
