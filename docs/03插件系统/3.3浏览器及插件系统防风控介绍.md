# 3.3 浏览器及插件系统稳定发布说明

> 本文介绍 WeMediaBaby（媒小宝）在浏览器层面和插件层面的稳定发布策略。当前默认方向是“真实浏览器稳定模式”：使用可见的本机 Chrome、独立账号 Profile、精简启动参数和风险提示停机；`compat_stealth` 仅作为旧兼容/诊断模式保留，不作为默认发布策略。

---

## 一、浏览器技术选型

### 1.1 为什么使用可见的本机 Chrome？

WeMediaBaby 默认采用 **Playwright 驱动本机安装的 Chrome（稳定版）**，发布流程优先使用可见窗口，而非 Chromium 开发构建或无头浏览器。这一选择的重点是降低异常浏览器信号、提升登录态和发布流程稳定性：

- **真实 Chrome 的证书链、更新节奏、GPU 渲染路径、字体渲染和媒体能力**更接近普通 Windows 桌面环境。
- **登录 Cookie 依赖 Chrome 原生持久化 User Data 目录保存**，不再依赖 Playwright `storage_state` 作为启动时的登录态来源。
- **可见窗口发布**减少无头模式、虚拟视口和过多 CDP Emulation 调用带来的异常环境信号。

Playwright 的角色是"驾驶员"，Chrome 是"车辆"——Playwright 负责控制流程，真实的 Chrome 才是平台看到的浏览器。

### 1.2 关于 Patchright 和旧兼容模式

项目历史上保留了 `patchright`、`stealth.js` 等旧兼容能力，用于兼容某些页面或诊断历史问题。当前默认策略不再把“脚本伪装指纹”作为发布主线：

- 默认 `real_browser` 模式不注入 `stealth.js` / `stealth_minimal.js`，也不主动覆盖浏览器 JS 指纹。
- `compat_stealth` 只作为旧兼容/诊断模式使用，启用后才会注入 legacy `stealth.js` 并携带旧的 WebRTC 等兼容参数。
- 小红书等高风险平台被纳入 `STRICT_REAL_BROWSER_PLATFORMS`，即使配置成 `compat_stealth`，也会强制走可见真实 Chrome 且跳过 JS 注入。

### 1.3 两种启动模式：真实浏览器模式 vs 旧兼容模式

系统通过 **BrowserLaunchPolicy（启动策略）** 统一管理两种工作模式，可在应用配置中切换：

| 模式 | 配置值 | 说明 |
|---|---|---|
| **真实浏览器模式**（real_browser）| `real_browser` | 默认模式。使用可见本机 Chrome、独立账号 Profile、精简启动参数；不注入 JS 指纹脚本，不改写 `navigator` / Canvas / WebGL 等浏览器 API |
| **旧兼容模式**（compat_stealth） | `compat_stealth` | 旧兼容/诊断模式。保留 legacy `stealth.js` 注入和 WebRTC 等旧参数；默认不用于发布 |

`STRICT_REAL_BROWSER_PLATFORMS` 集合中定义了必须使用真实浏览器模式的平台（目前为小红书）。这些平台无论全局配置如何，都会强制使用可见窗口和真实 Chrome，并跳过 legacy JS 指纹改写。

## 二、账号隔离与持久化

### 2.1 每账号独立 User Data 目录

每个平台账号拥有完全隔离的 Chrome User Data 目录，路径由 `PathManager` 统一管理，格式为：

```
%LOCALAPPDATA%\WeMediaBaby\data\{platform}\{profile_folder_name}\browser\user_data
```

账号文件夹名使用创建时生成的固定 UUID（`profile_xxx` 格式），不以账号昵称命名，防止改名后路径变化导致登录态丢失。

**隔离效果：**
- 不同账号之间的 Cookie、缓存、浏览记录完全不共享。
- 每个账号对应的浏览器进程打开后看到的是"全新"的 Chrome 会话，与其他账号互不干扰。
- 多账号并发发布时各自维持独立上下文，不会相互污染。

### 2.2 登录态持久化原理

登录成功后，Cookie 和会话信息自动保存在账号专属的 Chrome User Data 目录中（由 Chrome 原生的 SQLite 数据库管理）。下次启动同一账号的浏览器时，Chrome 会自动恢复已登录状态，**无需重新登录**。

同时，`ProfileManager` 会在浏览器关闭时将 `storage_state.json` 快照另存一份作为备份，供诊断和排障使用。

### 2.3 启动前防残留进程干扰

每次启动账号浏览器前，系统会主动检查并终止可能遗留的 Chrome 进程。这些进程如果仍在占用账号的 User Data 目录，会导致新的 Chrome 实例因"目录被锁定"而立即崩溃（`TargetClosedError`）。清理策略分两阶段：先通过已注册的 PID 精准清理，再对全机 Chrome 进程做路径匹配扫描兜底。

## 三、账号环境配置与 legacy 指纹档案

项目保留了账号级指纹档案，用于历史兼容、环境诊断和 `compat_stealth` 模式。默认 `real_browser` 模式不会通过 JS 覆盖这些浏览器 API，避免因为脚本改写本身形成新的异常信号。

### 3.1 指纹配置的生命周期

每个账号在首次启动浏览器时，系统会随机生成一份指纹配置（`fingerprint_config.json`），此后每次启动都加载同一份配置。该配置当前主要用于 `compat_stealth` 旧兼容模式、诊断日志和历史配置兼容。

指纹配置包含以下维度的参数：

| 类别 | 具体参数 |
|---|---|
| **User Agent** | Chrome 主版本号、完整 UA 字符串 |
| **硬件参数** | CPU 核心数、设备内存、CPU 型号 |
| **显卡参数** | WebGL 渲染器型号、WebGL 厂商 |
| **屏幕参数** | 分辨率、可用区域、色彩深度 |
| **Navigator 属性** | platform、maxTouchPoints、vendor 等 |
| **语言与时区** | languages 列表、locale、timezone_id |
| **UA-CH 客户端提示** | brands、platform、architecture、bitness 等高熵字段 |
| **Canvas 指纹** | 每账号固定的噪声种子和强度等级 |
| **音频指纹** | AudioContext 噪声种子 |
| **网络参数** | effectiveType、downlink、rtt |
| **电池状态** | 充电状态、电量百分比 |
| **虚拟地理位置** | 纬度、经度、精度（可选启用） |

### 3.2 整机档案：硬件参数的真实性

为避免"CPU 核心数多但显卡是低端核显"这种明显矛盾的假指纹，系统维护了一套**整机硬件档案**（`hardware_profiles.py`），涵盖三个档位的真实机器配置：

- **入门档**：适合 4 核心 / 8GB 内存 / Intel UHD 核显或低端 AMD 核显
- **主流档**：适合 8 核心 / 16GB 内存 / GTX 1660 至 RTX 3060 级别独显
- **高端档**：适合 12-32 核心 / 32GB+ 内存 / RTX 4070 至 RTX 4090 级别独显

随机生成指纹时，系统从档案中整体取一条真实机器的配置，而不是各参数独立随机。这样生成的组合（如"RTX 4090 + 32 核 + 64GB"）是真实存在的整机，不会出现难以解释的硬件矛盾。

WebGL 厂商（`webgl_vendor`）始终由 WebGL 渲染器（`webgl_renderer`）自动推导，确保两者一致（例如渲染器写 NVIDIA 的，厂商就是 `Google Inc. (NVIDIA)`）。

### 3.3 指纹一致性校验

每次加载指纹配置时，`FingerprintConsistencyChecker` 会自动检查并修复如下问题：

- **屏幕参数矛盾**：如"可用宽度超过屏幕宽度"或"颜色深度与像素深度不一致"
- **硬件参数矛盾**：如"高端显卡配低端内存"、"高核心数配极低内存"
- **UA 与 Platform 矛盾**：如 UA 显示 Windows 但 platform 字段是 MacIntel
- **语言与时区矛盾**：如 locale 是 zh-CN 但时区不在亚洲
- **UA-CH 与 UA 矛盾**：如 UA 显示 Windows 但 ua_ch.platform 是 macOS
- **CPU 型号与硬件不匹配**：从整机档案中自动换算一个匹配的真实 CPU 型号

校验后若有字段被修正，会自动写回 `fingerprint_config.json`，保持文件与内存状态同步。

### 3.4 User Agent 与 Chrome 版本动态对齐（仅 compat_stealth）

在 `compat_stealth` 模式下，UA 中的 Chrome 主版本号会在启动时自动检测本机安装的 Chrome 版本（读取注册表），并将指纹配置中的 UA 版本号对齐到本机实际版本。

默认 `real_browser` 模式不主动传入自定义 UA，直接使用本机 Chrome 的真实 UA 和浏览器能力。

## 四、Legacy JS 兼容脚本（仅 compat_stealth）

在 `compat_stealth` 旧兼容/诊断模式下，系统会在每个页面加载前通过 Playwright 的 `add_init_script` 机制注入一段自定义 JavaScript（`stealth.js`）。默认 `real_browser` 模式不会执行本节能力，不会注入 `stealth.js` 或 `stealth_minimal.js`。

### 4.1 硬件与屏幕参数覆盖

脚本通过 `Object.defineProperty` 重写 `navigator.hardwareConcurrency`、`navigator.deviceMemory`、`screen.width/height` 等属性的 getter，使其返回指纹配置中预设的值，而不是真实宿主机器的参数。

### 4.2 WebGL 厂商与渲染器伪造

脚本 Hook 了 `WebGLRenderingContext.prototype.getParameter`（同时覆盖 WebGL2），对查询参数 37445（厂商）和 37446（渲染器）的调用返回预设字符串，而不是底层 GPU 驱动的真实值。

### 4.3 隐藏自动化标识

最关键的一步是将 `navigator.webdriver` 置为 `undefined`。为了应对各平台的原型链检测，脚本将拦截器 getter 的 `toString()` 伪装成了 `[native code]`，防止被风控系统通过探测方法特征嗅探出篡改痕迹。脚本还清理了 `window.__playwright`、`window.__puppeteer`、`window.__selenium` 等各种自动化框架的全局标记。

注意：项目已放弃在命令行参数中使用 `--disable-blink-features=AutomationControlled`，因为稳定版 Chrome 会将其标记为"不受支持的命令行标记"并在页面顶部显示黄色警告横幅，这本身就是一个异常浏览器信号。默认 `real_browser` 模式也不再改用 JS 去隐藏该字段；只有 `compat_stealth` 旧兼容模式仍保留 legacy JS 处理。

### 4.4 Navigator 扩展属性

脚本伪造了 `navigator.platform`、`navigator.maxTouchPoints`、`navigator.vendor`、`navigator.vendorSub`、`navigator.productSub` 等属性，确保与指纹配置中的 Windows 桌面环境声明一致（例如桌面环境 `maxTouchPoints` 应为 0，移动设备才有触控点）。

### 4.5 浏览器插件列表伪造

空插件列表（`navigator.plugins` 为空数组）是无头浏览器或精简 Chromium 的典型特征。脚本伪造了三个真实 Chrome 常见的插件（Chrome PDF Plugin、Chrome PDF Viewer、Native Client），使插件列表看起来正常。

### 4.6 UA-CH 客户端提示伪造

`navigator.userAgentData` 是现代 Chrome 新增的客户端提示接口，包含 brands（品牌列表）、platform、mobile 等基础信息，以及 architecture、bitness、uaFullVersion 等高熵字段。脚本覆盖了整个 `userAgentData` 对象，使其与指纹配置的 `ua_ch` 字段完全匹配，防止平台通过对比 UA 字符串与 userAgentData 来发现伪造痕迹。

### 4.7 Canvas 指纹噪声

Canvas 指纹是指通过在 Canvas 上绘制文本或图形，然后导出图片数据，不同机器/浏览器的渲染结果存在细微差异，可用于识别浏览器。

脚本 Hook 了 `HTMLCanvasElement.prototype.toDataURL`、`toBlob` 以及底层的 `getImageData`，在导出图像数据前，对像素值施加基于账号专属种子的伪随机噪声（基于 LCG）。**每个账号的噪声种子不同，因此不同账号的 Canvas 指纹不同；同一账号的种子固定，因此每次运行的指纹稳定一致。**补全 `getImageData` 路径能防住试图绕过 `toDataURL` 的高级检测库。

### 4.8 音频指纹噪声

类似 Canvas 指纹，AudioContext 也可被用来生成音频指纹。脚本通过 Hook `AudioContext` 的振荡器，在音频数据中加入基于种子的微小偏移，使音频指纹也具备账号级别的唯一性和会话内的稳定性。

抖音平台由于自身会主动检测音频环境，音频噪声补丁默认对抖音关闭，避免干扰音乐选择功能。

### 4.9 WebRTC IP 泄露防护

即使通过代理上网，WebRTC 也可能通过 ICE 候选协议泄露本机真实 IP。脚本 Hook 了 `RTCPeerConnection.createOffer`，在 SDP 中将所有真实 IP 地址替换为 `0.0.0.0`，并删除所有候选行。同时在浏览器启动参数中设置了 `--webrtc-ip-handling-policy=default_public_interface_only`，从底层限制 IP 暴露范围。

### 4.10 Media Devices 伪造

`navigator.mediaDevices.enumerateDevices()` 会列出系统中的麦克风、摄像头、扬声器等设备。脚本伪造了一组真实 Windows PC 典型的设备列表（Realtek 声卡 + 普通摄像头），避免设备列表为空或异常。

抖音平台由于需要真实的媒体权限来支持音乐选择功能，媒体设备伪造对抖音默认关闭。

### 4.11 其他细节伪造

- **焦点与可见性伪造**：自动化脚本常在后台运行，导致 `document.hasFocus()` 为 false、`visibilityState` 为 hidden，这些是致命的机器特征。脚本强制将其伪造为可见激活状态，并阻断 `visibilitychange` 事件。
- **performance.now() 时序抖动**：给微秒级计时器加入 ±0.08ms 的随机抖动，打破机器执行时序绝对精确的特征。
- **Intl 国际化**：统一时区为 `Asia/Shanghai`，与 Playwright 的 `timezone_id` 参数一致，防止 JS 中的时区探测与浏览器声明的时区不符。
- **Date.getTimezoneOffset**：强制返回 `-480`（UTC+8 的偏移量），与时区声明一致。
- **window.outerWidth/outerHeight**：无头模式下这两个值为 0，是典型的无头检测指标。脚本在检测到为 0 时将其覆盖为合理的有头浏览器值。
- **Headless 额外特征清理**：补充了 `window.speechSynthesis` 和 `window.screen.orientation` 等常在无头模式中缺失的属性兜底。
- **Battery API**：伪造电池状态为充电中、电量 50%-100%，避免无电池信息被识别为服务器环境。
- **Network Connection API**：伪造网络连接类型为 4G/WiFi、下行带宽和 RTT 延迟。
- **字体指纹防护**：Hook `document.fonts.check()` 和 `document.fonts.load()`，对白名单之外的字体返回"未安装"，防止通过字体枚举建立唯一指纹。
- **chrome 对象补全**：在 `window.chrome` 对象缺失时自动补全 `runtime`、`loadTimes`、`csi`、`app` 等属性，避免因 chrome 对象不完整暴露非标准环境。

## 五、浏览器启动参数治理

### 5.1 忽略 Playwright 默认注入参数

Playwright 在启动 Chrome 时会自动注入一些参数，其中部分参数会暴露自动化特征：

- `--enable-automation`：Chrome 会在地址栏下方显示"Chrome 正受到自动化测试软件的控制"的信息栏（InfoBar），平台 JS 也可通过检测该信息栏存在来判断自动化。
- `--disable-blink-features=AutomationControlled`：稳定版 Chrome 不支持此参数，会显示黄色警告横幅。
- `--no-sandbox`：关闭沙箱是典型的 CI/CD 环境特征。
- `--disable-popup-blocking`：关闭弹窗拦截会让平台 JS 的 `window.open()` 弹窗无节制显示。

系统通过 `ignore_default_args` 参数告知 Playwright 不要注入上述参数。发布模式下如果沙箱启动失败，不再回退到 `--no-sandbox`，避免把关闭沙箱的异常参数带进平台后台。

### 5.2 视频号的特殊启动参数

微信扫码登录对启动参数非常敏感，对"--disable-extensions"、"--disable-component-extensions-with-background-pages"等禁用扩展的参数反应尤为强烈，容易在扫码成功后出现"登录失败，稍后重试"。

针对视频号平台，系统会额外保留这些参数（即不禁用扩展），并开启 Chromium 沙箱，使浏览器尽可能接近真实使用状态。

### 5.3 防止"恢复页面"弹窗

如果浏览器上次异常退出，Chrome 下次启动时会弹出"要恢复页面吗？"的确认弹窗（InfoBar）。这个弹窗会遮挡发布操作区域，导致点击失效。系统通过三重机制防止：

1. **修改 Local State 文件**：在浏览器启动前将 `profile.exit_type` 改为 `"Normal"`，告知 Chrome 上次是正常退出。
2. **修改 Default/Preferences 文件**：同样设置 `profile.exit_type` 为 `"Normal"` 作为双重保险。
3. **启动参数兜底**：`--no-first-run`、`--disable-session-crashed-bubble` 作为最后防线。

## 六、虚拟地理位置

系统支持为每个账号配置虚拟地理位置（`virtual_geo`）。启用后，Playwright 会通过 Context 级别的 `set_geolocation` API 向浏览器注入指定的经纬度，使浏览器 Geolocation API 返回预设坐标，而不是宿主机的真实位置。

设计上将虚拟地理位置与 IP 归属地区分对待——出口 IP 的地理推断通常是运营商接入点，不等于用户真实城市；虚拟地理位置让浏览器级别的定位与实际业务城市保持一致，可配合代理 IP 使用。

视频号平台由于定时发表功能依赖北京时间语义，即使指纹中配置了其他时区，系统也会将视频号浏览器的 `timezone_id` 强制覆盖为 `Asia/Shanghai`，防止定时时间与后台时间偏差。

## 七、行为层节奏控制

浏览器环境解决的是"看起来像正常桌面 Chrome"，行为节奏解决的是"操作起来更接近真实用户"。

### 7.1 拟人鼠标移动与轨迹过冲

`HumanBehavior.mouse_move()` 实现了基于**三次贝塞尔曲线**的鼠标移动轨迹。
- **动态控制点**：移动时生成完全随机比例的控制点，摆脱固定的弧线定式；并在每个插值点加入随机微小抖动，整体效果与人手移动高度相似。
- **过冲模拟（Overshoot）与徘徊**：由于真人操作的误差，系统有 20% 的概率会在点击前“滑过头”（多移 10-30 像素），随后伴随短暂的“悬停徘徊与微抖”（`hover_and_jitter`），再缓慢回弹修正至真实目标坐标。

点击操作不会总是点在元素中心，而是在元素有效区域内随机选一个点（`click_in_bounds`），从视口内的随机位置出发，沿贝塞尔曲线移动到目标点再点击。

### 7.2 拟人键盘输入

文字输入通过逐字符打入实现，每个字符之间有 50-150ms 的随机间隔。大写字母、数字、特殊符号的输入略慢（间隔乘以 1.5 倍），模拟真实打字时的节奏变化。还会以 2% 的概率随机打错一个字符，然后立即 Backspace 删除，进一步增加自然感。

### 7.3 步骤前随机浏览

在每个发布步骤执行前，以约 40% 的概率触发"随机浏览"动作：随机选择在页面内小幅滚动、随机移动鼠标，或两者都做。这模拟了用户在操作前习惯性地看一眼页面、随手移动鼠标的行为，打破"步骤一结束就立即下一步"的机械节奏。

### 7.4 步骤间随机延迟

每个发布步骤完成后会自动插入随机间隔（`step_interval`），默认基准为 0.5 秒，随机增加 0-2.5 秒的抖动，并受 `speed_rate`（发布速度系数）影响。`speed_rate` 可在 UI 中配置，范围 0.1-2.0，允许用户在速度和安全性之间权衡。

单次操作前后也有 `operation_delay`，默认 0.5-3 秒随机，同样受 speed_rate 和 `delay_jitter_ratio` 影响。

### 7.5 高层认知暂停（CognitivePause）

在各个独立的 `step_interval` 之上，系统引入了宏观粒度的“用户分心”模拟。在步骤执行完成后，有 15% 的概率会触发长达 20-120 秒的认知暂停，模拟用户写文章时接个电话或构思文案的行为。在此长暂停期间，还会伴随偶发的小幅度页面上下滚动，作为防假死保活手段应对平台的页面状态检测。

### 7.6 风控冷却等待

如果平台返回"操作频繁"、"稍后重试"等风控提示，系统会触发 `cooldown_before_retry`，等待指定秒数（由平台配置文件设定）后再重试。这一等待时间由各平台在 `config/platforms/*.json` 中单独配置，可根据平台风控敏感度调整。

### 7.7 拟人物理滚动（Ease-in-out Rollback）

传统的 `mouse.wheel` 都是匀速且单向的滑动，极易被平台风控识别。系统底层重构了滚屏逻辑：
- **抛物线加减速**：单次滑动被拆分为多段，步幅呈现“中间大、两头小”的二次函数抛物线权重，真实还原手指拨动滚轮或滑屏的动量与阻尼物理惯性。
- **偶发回滚机制**：在顺向滑动中，有 15% 的概率触发小幅度的反向滑动，模拟用户“滑得太快回头看一眼”的不专注行为。

### 7.8 流程前后预热与驻留

- **发布前预热（Warmup）**：进入发布页后，不再立即填写表单，而是利用独立的预热步骤耗时 15-40 秒钟执行随机的页面浏览与鼠标游走，铺垫真实用户的意图。
- **发布后驻留（Post-Browse）**：传统脚本任务成功后会立即关闭浏览器。系统引入驻留机制：发布完成后随机停留 15-40 秒，期间穿插随机鼠标移动与上下滚动，稀释机器操作评分，避免“秒退”引发账号异常。

## 八、平台插件系统与稳定发布分工

### 8.1 插件体系概览

平台插件分为两类接口：

- **LoginPluginInterface（登录插件）**：负责账号添加流程，提供登录 URL、检测登录状态和提取账号信息三个核心能力。
- **PublishPluginInterface（发布插件）**：负责内容发布，提供发布表单字段定义和执行发布操作两个核心能力。

目前已注册的平台包括：

| 类别 | 平台 |
|---|---|
| 社区开源插件 | 抖音（douyin）、快手（kuaishou） |
| Pro 可选插件 | 微信视频号（wechat_video）、小红书（xiaohongshu）、哔哩哔哩（bilibili）、微博（weibo）、头条号（toutiao）、百家号（baijiahao）、多多视频（duoduoshipin）、企鹅号（qiehao） |

### 8.2 插件加载策略

默认采用**按需加载**：`PluginManager` 在首次调用某平台的 `get_login_plugin()` 或 `get_publish_plugin()` 时才进行 import 和实例化，结果缓存复用。这样可以避免启动时导入所有平台的重型依赖（如 playwright、各平台特有库），加快应用启动速度。

设置环境变量 `PLUGIN_EAGER_INIT=1` 可切换为启动期全量静态导入模式，主要用于兼容旧行为和打包时的模块收集排查。

Pro 插件缺失在 OSS 模式下被视为正常降级，不会阻止应用启动。

### 8.3 平台插件内的稳定发布分工

各平台插件的发布步骤链（基于 `GenericStepRunner`）与浏览器稳定发布能力的分工如下：

- **插件负责**：平台特定的 UI 选择器操作（上传文件、填写标题、选封面、点击发布按钮等）。
- **风险控制层负责**：每个步骤前的随机浏览、步骤间隔延迟、拟人点击/输入、风险提示识别后的停机保护。
- **浏览器层负责**：真实 Chrome 启动、账号 Profile 隔离、启动参数治理、沙箱策略和 legacy `compat_stealth` 兼容脚本。

这种分层设计使得新增平台插件时，开发者只需专注于平台特定的 UI 自动化逻辑；浏览器稳定性、风险提示停机和诊断截图由框架统一提供。

### 8.4 诊断能力

发布步骤失败时，系统自动触发诊断截图和 DOM 快照，保存到 `%LOCALAPPDATA%\WeMediaBaby\debug\screenshots` 目录，并记录失败步骤名和失败原因。开发者无需手动重现即可通过快照了解失败时的页面状态，大幅降低自动化调试成本。

## 九、平台差异化配置

不同平台的风控策略差异显著，系统在 `config/platforms/*.json` 中为每个平台维护独立的配置，可调整的参数包括：

- **请求超时**：页面加载、元素等待的超时时长
- **发布间隔**：同一平台两次发布之间的最短间隔（`respect_platform_interval` 可全局开关）
- **浏览器可见性**：是否强制有头模式（`force_visible_publish`）
- **风控停止策略**：检测到风控提示时是否立即停止（`stop_on_risk_prompt`）
- **发布节奏参数**：`step_interval_base_seconds`、`operation_delay_min_seconds` 等

这些配置的分离使得平台风控策略的调整只需修改配置文件，不需要改动插件代码。

## 十、总结

WeMediaBaby 的浏览器发布体系采用**真实环境优先、旧兼容能力后置**的策略：

1. **环境层**：使用可见本机 Chrome + 账号级别隔离 User Data 目录，避免复用用户日常 Chrome 默认 Profile。
2. **启动参数层**：过滤 Playwright 默认自动化参数，真实模式只保留必要稳定性参数，发布模式不回退 `--no-sandbox`。
3. **JS 注入层**：默认不注入 JS 指纹脚本；`compat_stealth` 仅作为旧兼容/诊断模式保留。
4. **行为层**：贝塞尔曲线鼠标移动、逐字输入、随机延迟和随机浏览，使操作节奏更接近人工操作。
5. **风险保护层**：识别平台风险提示后停止同账号后续任务，并保留异常关闭/非正常退出进入账号健康状态的实现入口。

上述各层相互配合，在提高发布成功率的同时，尽量降低异常浏览器环境和异常操作节奏带来的账号风险。由于各平台规则持续更新，浏览器策略和风险保护也需要持续维护和迭代。
