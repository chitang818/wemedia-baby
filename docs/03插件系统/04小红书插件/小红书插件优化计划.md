## 二、核心问题深度分析

### 问题一（🔴 最高优先级）：JS 直接调用 btn.click() 被平台识别

**问题位置：**

1. **`_xhs_submit_probe.py` L82** — 发布按钮主路径：
   ```javascript
   btn.click();  // ← 在 Shadow DOM 内直接 JS 调用 click()
   ```
   这是整个发布流程最终的点击操作，当前**主路径是 JS click**，鼠标坐标点击只是兜底。

2. **`step_06A_original_declaration.py` L477-L491** — 原创协议勾选：
   ```javascript
   box.click();  // ← 通过 evaluate 直接 JS 点击 checkbox
   el.click();   // ← 同上
   ```

3. **`step_02_entry.py` L118** — 发布入口点击降级：
   ```python
   await btn.click()  # ← 无人类行为包装的原始 click
   ```

**为什么危险：**
- JS 触发的 `click()` 事件与真实鼠标点击在以下方面存在显著差异：
  - **无 MouseEvent 坐标链**：isTrusted=false，无 clientX/Y、screenX/Y 轨迹
  - **无 pointerdown → pointerup → click 事件序列**：直接触发 click，缺少前序鼠标按下/释放
  - **无焦点转移**：真实点击会先触发 `mousemove → mouseenter → focus`，JS click 不触发
  - **无 composedPath()**：Shadow DOM 内的 JS click 不会在主文档产生事件冒泡路径
- 小红书平台已在 2025 年后的客户端代码中加入了 `isTrusted` 检测和事件序列完整性校验

**当前兜底逻辑的问题：**
```python
# step_08_submit.py L607-L611
if await _click_xhs_publish_via_sr(page, primary_label, metadata, config):
    return  # ← JS click 成功就直接返回，不走鼠标点击
raise RuntimeError(...)  # 只有 JS 失败才报错
```
即：当前 **JS click 是主路径，鼠标坐标点击只是 JS 失败后的兜底**，这和期望的反风控策略恰好相反。

### 问题二（🔴 高优先级）：JS 直接写入 input value

**问题位置：** `step_07_settings.py` L518-L529

```python
await page.evaluate(
    """([el, v]) => {
        el.focus();
        el.value = v;                                    // ← 直接写 value
        el.dispatchEvent(new Event('input', {...}));    // ← 伪造 input 事件
        el.dispatchEvent(new Event('change', {...}));   // ← 伪造 change 事件
    }""",
    [handle, st_str],
)
```

**为什么危险：**
- 真实用户输入时，每个字符都会触发：`keydown → keypress → input（带完整 InputEvent） → keyup`
- 伪造的 `new Event('input')` 缺少 `InputEvent` 的 `inputType`、`data`、`isComposing` 字段
- 此外，真实输入的 `input` 事件 `isTrusted=true`，而 `dispatchEvent` 创建的事件 `isTrusted=false`
- 小红书的表单框架（基于 Vue3 响应式）已知会监听这些字段的差异

### 问题三（🟠 高优先级）：Shadow DOM 内 JS 点击的替代方案不完善

**`_xhs_submit_probe.py` 中 `click_via_sr` 函数的问题：**

发布按钮 `xhs-publish-btn` 使用 `closed` Shadow DOM，`shadowRoot` 对外不可见，当前通过 `el._sr` 这个内部属性访问。这本身是一种 hack，平台可能随时修改。

更重要的是：即便坐标点击有效，当前的鼠标移动路径存在缺陷：
```python
# step_08_submit.py L406-L407
from_x = _random.uniform(0, max(1, vw))  # ← 起点过于随机
from_y = _random.uniform(0, max(1, vh))  # ← 可能从屏幕角落直线飞来
```
没有使用贝塞尔曲线，直接 `mouse.move` 再 `mouse.click`，缺少加速度模型。

## 三、优化方案（按优先级排序）

### 方案一：将 JS click 替换为真实鼠标坐标点击（P0 — 立即执行）

**目标文件：** `_xhs_submit_probe.py`、`step_08_submit.py`

**核心思路：** 将「JS click 为主路径」彻底调转为「真实鼠标点击为主路径，JS 只用于获取坐标」

**实施步骤：**

1. **修改 `_xhs_submit_probe.py`：**
   - 保留 `_SR_RED_BUTTON_CENTER_JS` 用于获取按钮坐标
   - **删除** `_SR_CLICK_RED_BUTTON_JS` 中的 `btn.click()`，改为只返回坐标
   - `click_via_sr` 函数改名为 `get_sr_button_center`，只返回坐标，不执行点击

2. **修改 `step_08_submit.py` `_click_submit_with_fallback`：**
   ```python
   # 改后逻辑（伪代码）：
   async def _click_submit_with_fallback(...):
       # 1. 通过 _sr 获取按钮坐标（不再 JS click）
       cx, cy = await get_sr_button_center(host, primary_label)
       if cx is not None:
           # 2. 用贝塞尔曲线鼠标移动 + 真实 mouse.click
           await _human_mouse_click(page, cx, cy, metadata, config)
           return
       # 3. 兜底：宿主元素 bounding_box 推算坐标
       box = await host.bounding_box()
       if box:
           await _human_mouse_click(page, box["x"]+box["width"]-120, ...)
   ```

3. **新增 `_human_mouse_click` 辅助函数：**
   - 从当前鼠标位置（随机页面区域）以贝塞尔曲线移动到目标
   - 移动步骤 20-35 步（对应约 300-500ms 移动时间）
   - 到达目标前 5-10px 处轻微抖动（模拟手抖）
   - mousedown → 随机等待 60-180ms → mouseup → click 完整序列

### 方案四：改进 Shadow DOM 访问策略（P1 — 尽快执行）

**背景：** `el._sr` 是 Chromium 内部实现细节，平台可能已通过重写 `_sr` 属性来检测或干扰访问。

**替代方案：**

1. **方案 A（推荐）：使用 CDP（Chrome DevTools Protocol）访问 Shadow DOM**
   - 通过 `page.expose_function` 或直接 CDP Runtime.evaluate，以更底层的方式穿透 Shadow DOM
   - 不依赖 `_sr` 这个内部属性
   
2. **方案 B：纯坐标点击（不读 Shadow DOM）**
   - 不访问 Shadow DOM，只通过宿主元素 `bounding_box` 推算发布按钮大致位置
   - 使用 `host.bounding_box()` 获取宿主坐标，右下角偏移点击（已有兜底逻辑）
   - 最简单，完全绕开 Shadow DOM 访问问题

**推荐立即改为方案 B（纯坐标点击），Shadow DOM 访问仅用于验证，不用于触发点击。**

## 五、技术参考：真实鼠标点击 vs JS click 差异对照表

| 属性 | 真实鼠标点击 | JS `element.click()` | JS `evaluate→btn.click()` |
|------|------------|---------------------|--------------------------|
| `isTrusted` | `true` | `false` | `false` |
| 事件序列 | pointerdown → mousedown → pointerup → mouseup → click | 仅 click | 仅 click（Shadow 内） |
| clientX/Y | 有真实坐标 | 0,0 | 0,0 |
| 事件 composedPath | 完整 | 完整（open Shadow）| 仅 Shadow 内 |
| 焦点转移 | 会触发 focus/blur | 不一定 | 不一定 |
| 视觉反馈（ripple） | 有 | 无 | 无 |

> ⚠️ **关键结论：** 平台只需检测 `event.isTrusted === false` 或 `clientX === 0 && clientY === 0` 即可识别所有 JS click 操作。这是当前风控触发的根本原因。

## 六、P3 阶段优化展望（残余 JS 脚本评估）

经过全面的代码扫描（`evaluate`, `.click()`, `.value =`），小红书插件**已经彻底消灭了所有带有风险的 JS 交互行为（如强行点击、强行赋值）**。目前残留的 JS `evaluate` 调用主要分为两类，评估及优化方案如下：

### 1. 视口滚动行为（中低风险）
- **残留位置**：`step_01_home`, `step_05_description`, `step_07_settings`, `step_08_submit` 均有使用 `window.scrollBy` 或 `scrollIntoView`。
- **风险评估**：虽然 JS 滚动不会触发带 `isTrusted: false` 的关键表单事件，但过度平滑或瞬间的跳转滚动仍缺乏人类拖拽滚动条或滚动鼠标滚轮的物理特征。
- **P3 优化方案**：
  - 弃用所有 JS `scroll` 调用。
  - 在 `HumanBehavior` 类中封装 `mouse_scroll(page, distance)` 方法。
  - 使用 Playwright 的 `page.mouse.wheel(delta_x, delta_y)` 配合贝塞尔步长衰减，模拟人手转动物理鼠标滚轮的停顿感（一段、一段地滚）。

### 2. DOM 状态探测与数据提取（无风险）
- **残留位置**：Shadow DOM 内按钮样式读取、话题标签文本提取、弹窗显隐状态检测等。
- **风险评估**：完全无风险。所有的读取都是 Read-only 操作，不会在浏览器事件循环中向平台派发任何动作事件，平台风控脚本无法区分这是爬虫读取还是浏览器自身的正常渲染流程。
- **P3 优化方案**：维持现状，确保只在非敏感数据的读取上使用。
| 2026-05-30 | 上传前鼠标悬停 0.8-2.2s | 降低 set_input_files 直接注入特征 |
